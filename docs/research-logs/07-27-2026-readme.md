# pactwright

**Run a one-person product company from a single Git repository. Agents do the work; you make the calls.**

- **Agents produce, you decide** — agents draft competing approaches, with the case against each; you choose what proceeds, with your reasoning attached.
- **Everything stays on the record** — six months later, “why don’t we use ML for bulk acceptance?” is one lookup: the decision, its rationale, and the UX principle that forced it.
- **Plans derive from evidence** — `/derive-cycles` regenerates the backlog from what the project knows minus what it has shipped. There is no roadmap file to keep current.
- **Effort scales with risk** — every intent gets a work class, 0–3: a typo fix is one commit; a core product flow gets rival proposals, critic review, independent verification, and your explicit sign-off.
- **One repository** — knowledge, code, incidents, decisions, and campaigns are plain files you can grep and diff. No pactwright-hosted control plane, no proprietary database, and no separate system to export from.

pactwright connects what your company knows to what it plans, builds, ships, learns, and says. Agents generate proposals, implementation, and evidence; consequential choices remain explicit human decisions.

In the command examples below, `●` marks a decision only you can make. Everything else can be delegated.

## How pactwright works

```text
Sources → Knowledge → Plans → Intents → Decisions → Changes → Evidence
             ↑                                           ↓
             └──────── Production and measurement ───────┘
```

1. **Knowledge records what the project currently believes** — user evidence, product constraints, strategy, operational learning, and delivery guidance.
2. **Plans derive from that knowledge** — pactwright finds the valuable, unshipped work, build cycles and campaigns alike, rather than asking you to maintain a parallel roadmap.
3. **Agents propose before they implement** — consequential work gets rival approaches, criticism, and explicit selection.
4. **Evidence closes the loop** — tests, releases, incidents, and campaign results feed back into the same connected record.

The same operating loop governs product delivery, production operations, creative work, and standing repository reviews:

> **Learn → Propose → Critique → Decide → Build → Verify → Measure → Learn**

## See it in action

Three connected moments from building *Kakeido*, a weekly spending-review app. It starts as an empty repository and a single UX specification.

### Day zero — a guided cold start

```text
You:  /next-actions
pactwright: Empty project. Exactly 3 moves — nothing else is actionable yet:
      1. Who is this for?       → /ingest docs/founding/user-research.md
      2. What are you building? → /ingest docs/founding/kakeido-ux-spec.md
      3. How do you sound?      → /ingest docs/founding/voice.md

You:  /ingest docs/founding/kakeido-ux-spec.md
pactwright: Captured. 23 claims extracted — "envelopes: Needs/Wants/Culture/
      Unexpected", "group before listing", "bulk actions must feel
      reversible", ... Approval proposal opened as PR #1.
      ● Merging it is your first decision on the record.

      [the other two founding documents follow]
pactwright: Core seeded. Unlocked: go-to-market — strategy, plan, positioning,
      each prompt pre-linked to the personas and bets it must build on.
      Your first /derive-cycles will be the founding build plan.
```

The repository begins with approved knowledge rather than an empty task board. What becomes actionable depends on what the project already knows. — commands: [Bring knowledge in](#bring-knowledge-in) · [Plan](#plan)

### From evidence to approved implementation

```text
You:  /derive-cycles
pactwright: Plan regenerated from knowledge minus shipped: 1. CSV import ✓ shipped
      2. weekly review flow ← next, unblocked, sized M
      3. categorisation rules  4. monthly plan  5. explore
      Nobody wrote this roadmap — it fell out of the graph.
      → /capture-intent <attached draft for cycle 2>

You:  /capture-intent "Weekly review flow: import → review brief → decision
      cards → group checks → looks safe → full scan → confirm week.
      Per the spec: lead with decisions, one job per screen."
pactwright: int-0007 · class 2 (core product surface). → /propose-contracts int-0007

You:  /propose-contracts int-0007
pactwright: 3 rival contracts:
      A  rules-first        "looks safe" from merchant history; ML later
      B  suggestion-first   model-ranked categories from day one
      C  hybrid             rules classify safety; model only inside
                            decision cards, where reasons are shown
      → /review-contracts int-0007

You:  /review-contracts int-0007
pactwright: UX critic: B risks violating "make automation inspectable".
      Cost critic: B adds recurring inference on every import.
      QA critic: A is trivially testable. ● Your pick.

You:  /approve-contract con-0007-c "inspectability requires rule-backed
      bulk accept; model confined to cards that show their reasons"
pactwright: Approved. Comparison and rationale kept forever — siblings rejected,
      on the record. → /decompose-lanes con-0007-c frontend-ui,domain-backend,test-verification

You:  /decompose-lanes con-0007-c frontend-ui,domain-backend,test-verification
pactwright: 3 briefs, each self-assembling its context by walking edges:
      frontend-ui carries the UX cards (a decision card = one spending, one
      reason, one suggestion); domain-backend carries the envelope model and
      "import is idempotent". test-verification is its own lane — the author
      never grades its own work. → /implement-brief brief-0007-ui

You:  /propose-patches brief-0007-ui 2 "bottom-sheet-flow,screen-per-step"
pactwright: 2 candidate implementations → /compare-patches brief-0007-ui

You:  /select-patch patch-0007-ui-a "bottom sheets keep the review one-handed —
      the core mobile acceptance test"
pactwright: ● Recorded. Per-lane evidence prepared; /integrate joins the lanes with
      a combined test run; /release-check when green; /post-deploy-review
      turns any surprise into new intent. The loop closes itself.
```

The approved rationale is not commentary attached after the fact. It becomes a constraint that later briefs, implementations, tests, and reviews must carry. — commands: [Plan](#plan) · [Build and ship](#build-and-ship)

### Production talks back

```text
pactwright: Ticket #142: duplicate spendings after CSV re-import. Severity S1,
      workflow "import transactions". → /investigate item-0142

You:  /investigate item-0142
pactwright: Two rival explanations, evidence attached:
      H1  idempotency failure on retry     for: log cluster, trace sample
      H2  bank exported overlapping rows   against: file checksums match
      Root cause is NOT confirmed — that takes evidence plus ● your sign-off.

You:  [you confirm H1]
pactwright: Bug recorded — it violates spec invariant "import is idempotent".
      Correction plan drafted: scoped, validated, reversible — a PR for
      ● your approval. The fix enters delivery like any other change.

You:  /ops-learn item-0142
pactwright: The ticket became: a regression test, a knowledge card, and a
      known issue until rollout completes. Occurrences since release: 0.
      Ticket → bug → correction → fix → release → invariant: one walkable chain.
```

Production does not create a disconnected incident archive. It changes what the product knows and what future work must prove. — commands: [Operate](#operate)

Every command ends by printing the next one, with real IDs. A day’s work is a chain you follow, not a system you navigate.

## Why pactwright?

AI-assisted development loses its context at the session boundary. Each new session starts from what the context file records — a snapshot of the project as it stood when the file was last maintained, not the decisions made since — so established context is reconstructed by hand, repeatedly. The artifacts that do persist drift: the roadmap, the code, and the public messaging each evolve on their own schedule, and a solo founder has no second reader to notice when they diverge. Documentation that has drifted quietly is worse than none, because it is trusted until it fails. pactwright addresses the root cause: the repository itself becomes the durable memory — knowledge, decisions, and messaging connected with provenance, and agent activity governed by recorded budgets and human gates.

- **Everything traces** — rationale stays attached to outcome: a ticket traces to the bug, the fix, the release, and the knowledge beneath it; a published post traces back to the strategy it expressed. Settled decisions carry their reasoning, so they are not re-litigated and past work does not have to be reverse-engineered.
- **Truth self-corrects** — knowledge carries a freshness clock, challenged conclusions flag their dependants before anything ships on them, and scheduled drift review catches what slips through — so recorded knowledge remains trustworthy over time.
- **Attention goes where it matters** — output that appears correct is not thereby verified, and tests written by the model that wrote the code are not an independent check. pactwright reviews work against the intent it was meant to serve, verification never uses the generating model, and routine repetition is absorbed — what surfaces is the new, the conflicting, and the decisions.
- **Agents are safe to scale** — every model call, regardless of provider, is recorded and budgeted with hard ceilings at a single runtime choke point; consequential decisions pass through a human gate, and overriding a gate places the override itself on the record. As one agent becomes several, the graph remains the single account of what happened, rather than parallel sessions each holding a divergent one.

## What pactwright manages

Five surfaces, one operating loop, one command group each — and one platform beneath them:

### Knowledge and planning

Capture documents, interviews, feeds, findings, and operational evidence as claims with provenance; pactwright reconciles corroboration and contradiction and tracks freshness. On a new project it also guides the filling: `/next-actions` surfaces the mandatory core — users, product, identity — in dependency order, and seeding it unlocks the go-to-market knowledge that orders the plan and defines the first launch tranche (walked in [Day zero](#day-zero--a-guided-cold-start)). From there both plans derive: `/derive-cycles` turns approved knowledge minus shipped work into software delivery cycles, and `/derive-creative-cycles` turns what is worth saying minus what has been said into campaign cycles. — [Bring knowledge in](#bring-knowledge-in) · [Plan](#plan)

### Delivery

Turn an intent into rival contracts, critic review, approved briefs, independent tests, competing patches, compliance evidence, release checks, and post-deployment learning. — [Build and ship](#build-and-ship)

### Operations

Route tickets, incidents, bugs, data corrections, known issues, and mitigations through the same evidence and approval model. Production learning returns to specifications and tests. — [Operate](#operate)

### Creative work

Derive campaigns from positioning and unsaid opportunities, generate competing concepts and assets, verify claims and voice, approve publication, then measure the outcome against targets selected before production begins. — [Tell the world](#tell-the-world)

### Standing review and governance

Run scheduled reviewers against stable repository snapshots, surface drift and stale knowledge, enforce model separation between generation and verification, and record budgets and spend. — [Keep it honest](#keep-it-honest)

### Orchestration

Declare any shape the surfaces above run — a delivery cycle, a campaign, a digest, a standing review, a one-time migration — as a workflow: a plan approved once against pinned truth, runs cheap and retryable against it, budget lines reserved before a token is spent. Defaults ship for every loop; the graph can derive new extensions and import community ones. — [Run workflows](#run-workflows)

## Quick start

Needs Git, a GitHub repository with branch protection, and at least one agent CLI — Claude Code, Codex CLI, Gemini CLI, or Grok Build, in any combination.

```sh
curl -fsSL https://raw.githubusercontent.com/your-org/pactwright/main/init.sh | bash -s my-product
cd my-product && claude    # or codex, gemini, grok
```

The script fetches the skeleton, detects your agent CLIs, and asks which to wire up. Prefer not to pipe shell, or want the GitHub-template or npx path? See [Installation](docs/installation.md).

Then:

- **Have a founding document?** `/ingest docs/founding/overview.md` — pactwright extracts what it says and proposes what the project should officially know. You approve by merging.
- **Not sure what to do?** `/next-actions` — on a new project it shows exactly three moves: capture your users, your product, and your identity. Completing them unlocks go-to-market, then content, then your first campaign and build plan. That guidance is itself a standing review — the [progression reviewer](#the-review-engine) reading your graph.

Before your first approval, switch on branch protection for `main` — pull-request reviews are how pactwright’s gates are enforced.

## Repository model

pactwright’s durable state is one typed-edge graph stored as versioned files:

```text
# The graph — canonical truth
specs/
  nodes/                  one file per node: intents, contracts, briefs,
                          decisions, evidence, releases, concepts, assets
  graph/edges.yaml        every relationship — one typed, schema-checked table
  schema/                 node and edge definitions that validation enforces

# Evidence and knowledge
sources/                  raw evidence: documents, interviews, feeds, tickets
knowledge/                approved claims, guidelines, runbooks — per domain
domains/                  the domain registry: steward, freshness, scope

# Production
items/                    operational items: incidents, corrections, known issues
context/changes/          every deploy, flag, and config change, recorded

# Behaviour — registries and agent files, all changed by ordinary PR
lanes/                    lane configs: implementer, skills, verifier
metrics/                  success measures, pinnable and scored
providers/                model vendors and conformance status
reviews/                  standing reviewer definitions
workflows/                workflow definitions: stages, gates, budgets,
                          triggers — the default catalog included
views/                    view definitions — DESIGN.md and other derived
                          documents, regenerated from recorded hashes
prompts/                  governed prompt templates
.claude/agents/           subagent roles
.claude/skills/           practice documents lanes load
.claude/models/           task-class model catalogues

# Derived — regenerated as the graph moves, never hand-edited
reports/                  plans, queues, boards, scoreboards
```

Four rules make this a graph rather than a pile of files:

1. **One writer** — only the graph-maintainer role writes under `specs/`; agents propose, humans approve.
2. **Nothing is deleted** — records are superseded, retracted, or overridden, always on the record.
3. **Edges are the truth** — every relationship lives in `edges.yaml`, which is why provenance is a walk, not a search.
4. **GitHub enforces it** — branch protection and CODEOWNERS gate the writes; generated Projects boards give read-only views; Git provides history, review, and reproducible snapshots.

## Extending pactwright

pactwright has no plugin API. Everything that shapes behaviour is a file changed through an ordinary reviewed pull request.

### Knowledge domains

```text
/register-domain legal
```

Carve out a new knowledge area. It gets a steward, a freshness clock, and its own gap list — by tomorrow `/next-actions` is nagging you about the privacy policy it noticed you do not have.

### Model providers

```text
/register-provider mistral
/ingest https://docs.mistral.ai/guides/prompting
```

Plug in a new vendor: one adapter, one conformance test, one PR — no call-site changes, every call leaves the same spend record. Then teach the project how to use it: ingest the vendor's prompting guide and its claims become guideline cards, trial-promoted and auto-applied to matching calls. Promoted cards can be distilled into a custom skill for lanes that work with the provider hands-on — grounded in the cards, so the cascade flags it when the guidance is superseded.

### Standing reviewers

```text
/register-reviewer security
```

Hire a standing critic that examines the repository on a schedule and files findings into your queue. Next month it blocks a session-replay intent for a missing retention policy — one file, new rules. See one run in [the repository reviews itself](#the-repository-reviews-itself); the starting roster is in [the review engine](#the-review-engine).

### Metrics

```text
/register-metric reply-rate
```

Declare how success is measured before work runs. Pin it as a campaign target; `/measure` scores it, and a miss comes back as a challenge to your strategy — never a silent shrug.

### Workflows

```text
/register-workflow release-train
/plan-workflow release-train month=aug
```

Declare a shape once — stages, gates, budgets, triggers — and every execution is a run of an approved, pinned plan: retries repeat exactly what was approved, improvements supersede with rationale, and spend is reserved before it happens. One-time shapes skip registration ceremony with `--once`; a chain you keep running by hand gets flagged by the progression reviewer with a paste-ready `/register-workflow`. Defaults ship for the delivery cycle, the creative cycle, ingestion digests, standing reviews, and extension updates.

### The marketplace

```text
/derive-extension skill
/import-extension github.com/acme/a11y-reviewer@1.2.0
```

Every extension is a versioned file, so the marketplace is Git. Deriving drafts a new extension from the knowledge that justifies it — a skill from promoted guideline cards, a reviewer from a recurring blind spot, a `DESIGN.md` view from your design truth — grounded so the cascade flags it when that knowledge moves. Importing vendors a community file with pinned provenance; publishing is pushing. Either way it earns the same reviewed PR as a hand-written file, and the `extension-update` workflow proposes upstream version bumps as diff-attached PRs — never merges them.

### Delivery lanes, subagents, and skills

```text
lanes/mobile-ui.md
```

A lane config answers three questions:

- **Who implements?** One subagent — for Kakeido's frontend, `ui-implementer`.
- **What does it know?** The skills it loads before touching a brief — community ones like `taste-skill`, plus homegrown, knowledge-grounded ones like `kakeido-design-tokens`.
- **Who verifies?** An independent lane — never the implementer itself.

In the reference: [agent and lane files](#agent-and-lane-files) · [Kakeido lane staffing](#kakeido-lane-staffing) · [adding a lane](#adding-a-lane) — one PR, three files.

## How it compares

**vs. a bare agent CLI** — powerful but stateless: context, decisions, and plans live in the session and whatever files you maintain by hand. pactwright makes the repository the memory every agent loads — knowledge, decisions, evidence, and outcomes, connected with provenance.

**vs. spec-kit / OpenSpec** — excellent at specification-driven *coding*. pactwright governs the whole operation: competing approaches are a first-class workflow, planning regenerates from knowledge minus shipped, production learning re-enters the record, and campaigns run and get measured on the same rails — with explicit, recorded human decision gates throughout.

**vs. nothing** — scattered notes, transient sessions, and a stale roadmap, replaced by one reviewable operating history.

## Extended workflows

The core walkthrough above shows the product-delivery loop. These examples show how the same model handles changing knowledge, generation guidance, campaigns, and scheduled review.

### Knowledge stays honest as it grows

```text
      [three weeks later, a pilot interview lands]
You:  /ingest sources/interviews/2026-06-pilot-3.md
pactwright: 9 claims. 7 corroborate existing cards — absorbed, confidence raised,
      no action needed. 1 contradicts kn-ux-0004 "never open into the
      transaction table". ● Contradiction in your queue — the cascade lists
      2 unshipped briefs built on the old assumption.
```

New evidence does not overwrite old conclusions silently. It either strengthens them, challenges them, or creates a new decision for the queue; changed knowledge then identifies the unshipped work that depends on it.

### Prompting knowledge is knowledge too

```text
You:  /ingest sources/articles/imagen-prompting-guide.md
pactwright: 6 claims routed to delivery/generation — "front-load subject and style",
      "state negative space explicitly", ... Trial proposed: A/B against the
      current guideline card on 10 matched image calls.
      ● Promotion takes comparative evidence, not vibes.

      [the trial runs under its budget; the variant wins 8/10]
pactwright: Guideline card kn-gen-0012 accepted. The runtime now applies it to every
      matching image call automatically — and pins it (guided-by) in each
      call's generation record, so any output walks back to the prompting
      knowledge that shaped it. Retired the day its scoreboard decays.
```

Prompting practices are treated like any other operational claim: tested, approved, versioned, traced to outputs, and retired when the evidence no longer supports them.

### A campaign travels the same rails

```text
You:  /derive-creative-cycles
pactwright: Creative plan from what's worth saying minus what's been said:
      1. launch announcement ← next: positioning card approved, product
         shippable, nothing published yet
      2. weekly-ritual explainer   3. import-privacy post
      → /capture-creative-intent <attached draft for cycle 1>

You:  /capture-creative-intent "Launch post + visuals: Kakeido makes the
      weekly money review a calm ritual, not a spreadsheet chore"
pactwright: cci-0003 · class 2 (touches positioning). → /propose-concepts cci-0003

You:  /propose-concepts cci-0003
pactwright: 3 rival concepts:
      A  "Five minutes on Sunday"   ritual-first, calm as the proof
      B  "Your money, decided"      decision-count hook
      C  "The anti-dashboard"       contrarian, attacks the category
      → /review-concepts cci-0003   voice and strategy critics weigh in

You:  /select-concept con-c-0003-a "the ritual IS the product"
pactwright: ● Selected. Success pinned BEFORE work runs: signups ≥ 40/week,
      review-completion ≥ 60%. → /decompose-assets — copy and image lanes
      fan out, each call budgeted, image calls guided-by kn-gen-0012.

You:  /verify-assets
pactwright: Copy claim "review a week in under 5 minutes" → traced to kn-ux-0009 ✓
      Image 2: headline illegible at feed size — RED, blocked. The verifier
      is never the model that generated the work. Fix queued.
      → /prepare-publication ● you approve → /record-publication

      [two weeks later, the measurement window closes]
You:  /measure pub-x-0031
pactwright: Signups 52/week — beat. Review-completion 48% — miss. The miss files a
      challenge against the onboarding assumption behind the concept;
      proposal in your queue. A miss is learning, never a silent shrug.
```

Creative work uses the same primitives as delivery: grounded intent, competing approaches, independent verification, explicit approval, and measured learning.

### The repository reviews itself

```text
      [Monday 06:00 — a scheduled Action, nobody at the keyboard]
pactwright: Review executed: ux-consistency v1.3 · scope: 14 screens, 9 UX cards,
      snapshot content-hashed. 2 findings filed into triage:
      F1  Explore has grown three chart widgets across recent briefs —
          spec says "Explore stays secondary"; cites kn-ux-0011 and the
          two briefs that added them
      F2  decision-card copy tone — duplicate, occurrence 3: corroborates
          the existing finding, raises its weight, costs you nothing
      ● Only F1 reaches your queue. Promotion is human, always.

You:  /review-roster
pactwright: ux-consistency   weekly    last: today      findings promoted: 4
      cost             monthly   last: 12 days    flagged: image spend +38%
      security         monthly   next run: 6 days
      Reviewers are files — /register-reviewer puts a new one on the roster.

      [you think F1 misreads the spec — so make it prove itself]
You:  /rerun-review rex-0047
pactwright: Repeated against the SAME snapshot: identical scope hashes, same
      catalogue pins, byte-comparable findings. F1 stands. The disagreement
      is now about the spec, not the run — challenge filed to kn-ux-0011,
      and the cascade will flag whatever was built on it.
```

A review execution pins its inputs so it can be reproduced. Repeated or corroborating findings gain weight automatically, but only a human-promoted finding can change the project’s official knowledge. The definition anatomy, the starting roster, and the reviewer that powers `/next-actions` are in [the review engine](#the-review-engine).

## Agent and lane files

Beyond the registries, the agents and their operating constraints are ordinary files you can edit, replace, or add.

| One file in… | …changes |
|---|---|
| **Subagents** · `.claude/agents/` | The roles — specification writer, critics, test writer, producers, and verifiers. A fintech-compliance critic joins the review panel as one Markdown file. |
| **Skills** · `.claude/skills/` | Portable `SKILL.md` practice documents a lane loads before working. |
| **Lane configs** · `lanes/` | Who implements each lane, which skills it loads, and who verifies it. Deviating from a default records a reason. |
| **Model catalogues** · `.claude/models/` | Eligible models per task class — copy, image, video, verification — plus a default. Verification never uses the model that generated the work. |
| **Guideline cards** · `knowledge/delivery/generation/` | Prompting techniques promoted on trial evidence, automatically applied to matching calls, and retired when their scoreboards decay. |
| **Runbooks** · `knowledge/operations/` | Pre-authorised incident actions — the only things allowed to act at 2 a.m. without waking you. |

Community skills drop straight in — `npx skills add Leonxlnx/taste-skill` — and any agent CLI reads them; the format is an open standard. Homegrown skills are `grounded-in` knowledge cards, so superseding a card makes the cascade flag the skill and every unshipped brief resting on it. Staffing is also on the record: deviating from a lane’s default records a reason.

## Deep mechanics

The machinery beneath the workflows. Full definitions live in the specifications under [Learn more](#learn-more); this is the working summary.

### The subagent roster

Each role is narrow by design — leanness comes from narrowness, not from collapsing responsibilities:

```text
Spec Writer           drafts rival candidate contracts from human intent
Spec Critic           attacks contracts: ambiguity, missing cases, scope creep
Specialist Critics    a named panel — Product, UX, Architecture, Security/
                      Privacy, Compliance/Risk, QA/Test, Reliability/Ops,
                      Cost/Maintainability, Release — routed by work class
                      and affected surface; each argues one axis
Decomposer            turns the approved contract into per-lane briefs
Code Archaeologist    reads the existing codebase first: files, patterns, risks
Implementation Agent  one candidate patch per brief; several compete when
                      trade-offs are real; never silently expands scope
Test Writer           owns test-verification; never the implementing role
Contract Reviewer     does each patch satisfy the approved contract?
Drift Reviewer        do specs, code, tests, docs, and evidence still agree?
Release Reviewer      readiness, rollback, monitoring, migrations, risk
Integration Reviewer  reconciles selected lane outputs into one contract-level
                      verdict: combined tests, conflicts, residual risk
Graph Maintainer      the only writer under specs/ — applies changes atomically,
                      never deletes (supersedes), revalidates after every write
```

### The review engine

A standing reviewer is one CODEOWNERS-gated definition file naming six things: a single **perspective**, a **scope** expressed as graph slices (never "the whole repo"), a **rubric** so runs are comparable across time and providers, a **cadence and triggers** (scheduled and/or event-driven — a cascade touched its scope, staleness crossed a threshold, a release merged), **model eligibility** through a task-class catalogue, and a **steward** whose queue its findings reach.

Each run mints a **review execution**: definition version, trigger, resolved scope with the content hash of every node read, provider pairing with its reason, findings, and — on a repeat — a link to the execution it repeats, read against the *recorded* snapshot so findings are byte-comparable. Findings enter triage as internal sources like any other evidence: duplicates corroborate rather than multiply, and a finding rejected in triage is a recorded rejection the next run can see — reviewers learn what the project has already declined. Where a definition names two providers, both run the same rubric over identical hashes; agreement raises confidence, disagreement is emitted explicitly for the steward, never averaged into false consensus.

The starting roster, extended by `/register-reviewer` exactly as domains are:

```text
ux-researcher          do the user journeys hold together?
product-strategist     are bets, roadmap, and intents still consistent?
gtm-strategist         does positioning still match personas and product truth?
architecture-reviewer  structural drift and constraint erosion per release
graph-auditor          graph hygiene: orphans, missing edges, stale statuses
voice-auditor          do published assets still comply with the voice cards?
cost-reviewer          provider spend vs. caps; budgets vs. actuals
generation-reviewer    are catalogue defaults and guideline cards earning
                       their keep against observed records?
progression-reviewer   what should happen next — coverage gaps in dependency
                       order, cycles ready for intake, lapsed reviews,
                       unscored publications, unanswered target misses
```

The last one is special: `/next-actions` **is** the progression reviewer's report — each suggestion names a gap, links its evidence, and carries one paste-ready command. Onboarding is not a mode; it is this same review at empty baseline, steering you from an empty graph to a running project in dependency order. With the workflow platform, its momentum scan extends to workflow signals — plans awaiting approval, halted runs, lapsed triggers, and recurring hand-run chains worth registering — so the platform is steered by the same report as everything else.

### The workflow platform

The general form of every loop above, built last so each default wraps something real. Three objects and two edges: a **Workflow Definition** (`workflows/<id>@<semver>.md` — archetype, parameters, stage DAG with gates, budget defaults, metrics, triggers, `recurring` or `one-time` lifecycle), an approved **Workflow Plan** pinning definition version, scope and config hashes, model pairings, budget lines, and gates, and a **Workflow Run** whose step records reference the records each stage's own machinery minted — never restate them. Retry is a sibling run against identical pinned inputs; improvement is a superseding plan; a plan resting on superseded truth refuses to run; a run that reaches a budget line halts and waits for override or amendment.

```text
software-delivery-cycle   intent → contracts → lanes → patches → release
creative-delivery-cycle   concepts → assets → verification → publish → measure
ingestion-digest          fetch → capture → triage → digest
standing-review           snapshot → rubric per eligible model → findings
extension-update          check pinned upstreams → diff-attached bump PRs
```

Wrapping adds orchestration only — the plan pin, sibling retries, stale-plan refusal, and reserved spend — and removing the wrapper leaves the loop running exactly as its own document specifies. Budget lines are declared in both tokens and currency at five scopes, reserved at admission, metered per call, reconciled per run: a blown period is refused before a token is spent, never discovered on the invoice. Stages may declare `corroborate` — two providers, one pinned manifest, disagreement reaching the gate explicit and unaveraged. Full definition in [the workflow runtime spec](docs/research-logs/07-24-2026-graph-native-workflow-runtime-spec-v13.md).

### Assertion kinds

Every claim and knowledge card declares what *kind* of statement it is, because "42% of users abandon the flow", "must not require account creation", and "we deferred multi-region" demand different treatment:

```text
observation | interpretation | hypothesis | requirement | constraint |
decision | recommendation | forecast
```

Promotion, contradiction, and freshness rules run over **domain × kind**. The key asymmetry: observations gain authority through corroborating *evidence* and decay over time; requirements, constraints, and decisions gain authority through *approval*, never decay empirically, and are challenged through governance — a class-3 event, not a statistical one. Forecasts hard-expire at their stated horizon.

### Disposition and impact class

Triage separates what happened from how much ceremony it earns. First the disposition: `irrelevant | duplicate | corroborating | incremental | novel | contradictory`. Then the impact class is **derived** from disposition × the authority the material actually touches — never from the domain name:

```text
0  irrelevant/duplicate/corroborating   automatic — log, link, or update counts
1  incremental                          additive only; auto-accepts after a
                                        veto window unless the steward objects
2  novel                                steward decision required
3  contradictory or dependency-breaking mandatory contradiction record and
                                        mandatory cascade; may need a Decision
```

Class follows consequences: a voice-card edit touching nothing is class 1; the same edit invalidating product copy and the content calendar — visible as the `constrains` edges it breaks — is class 3.

### The propagation matrix

When a card is challenged, superseded, or retracted, the cascade walks existing edges and emits, per dependent, exactly the consequence the matrix assigns — mechanical, not agent judgement:

| Dependent edge | Challenge | Supersession | Retraction |
|---|---|---|---|
| `depends-on` | review required | review; flagged outdated | invalidated pending re-validation |
| `supports` | confidence reduced | evidence re-pointed | evidence invalidated |
| `constrains` | review required | re-check against new constraint | constraint void; review |
| `implements` | review required | re-opened intent proposed | re-opened intent, expedited |

Consequences are graded proposals — from a steward ping up to a blocking drift item — and acceptance of every downstream change stays human. Supersession and retraction are distinct on purpose: superseded means *replaced by something stronger*; retracted means *the basis was invalid*, and everything derived from it is flagged with higher severity.

### Cycle derivation: DAG and waves

`/derive-cycles` compares two views of the one graph — what the project has established it should build against what it has built and proven — and finds three gap kinds: knowledge with no intent minted, intents still open, and intents whose grounding knowledge was since challenged. Gaps group into capabilities at the trade-off grain, dependencies are drawn, and the result is a dependency DAG rendered as **executable waves** — never a fake total order. Prioritisation follows an explicit precedence policy: legal/security/safety, then active incident risk, then hard dependencies, then committed obligations, then go-to-market sequencing, then uncertainty reduction. The guide is a generated report, propose-only: a human releases each cycle into `/capture-intent`.

### Signal ledger and materialisation

Two storage levels reconcile "every signal received" with "never a node per event". The append-only receipt ledger records everything — a thousand duplicate alerts in a paging storm are a thousand entries, and its dedup keys reject replayed webhooks. Graph nodes materialise only when a signal opens an item, changes severity, adds materially new evidence, confirms a recurrence, or requires an accountable response; everything else updates counts on nodes that already exist. A major incident lands in the graph as one incident with its evidence and responses — the storm stays in the ledger for forensics.

### Effective-state reconciliation

"Every production change is recorded" cannot be enforced by pipelines alone — console changes, dashboard flips, and emergency scripts bypass them. So a scheduled pass compares recorded state against actual state: deployed versus runtime version, recorded versus effective flags and configuration. Any unexplained mismatch becomes an **unrecorded-change finding** whose investigation names the actor, records the change retroactively with a break-glass annotation, and asks why the recording path was bypassable. The repository itself carries only opaque references to customer data — raw personal data, credentials, and message bodies stay in their source systems behind durable evidence references.
