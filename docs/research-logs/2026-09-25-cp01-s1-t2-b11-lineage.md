| Question / classification | Answer and rationale |
|---|---|
| Q79 — already specified; coverage missing | Core §44 cardinalities apply to every stored record, and Core §57 names "missing required lineage". A record that lacks its required upstream edge and has no core edge into any Intent direction is reported as missing required lineage, in one problem naming it and any records reached only through it. It changes no Intent's result, because it belongs to none, and complete-state validation fails. A record lacking its required edge but linked by supersession into a direction makes that direction affected (AC06, Core §44 cross-scope rules). AC11 has one case per record kind, with a reject Decision for the Decision case, and an unaffected-Intent control. |
| Q80 — missing observable | After an incomplete load, every derivation result exposes a diagnostic-only, non-executable indicator the verifier reads, and complete-state validation refuses execution. AC12 covers a malformed lifecycle file, a missing lock and an unexpected record file, with a complete-load control. The indicator's representation is an implementation choice. |
| Q81 — already specified; coverage missing | Core §44 "when one exists": a first authorisation after defer creates a Contract without a Contract supersession. AC07 adds `first-proceed-after-defer`, which yields contracted with no missing-supersession problem. The existing AC06 negatives still cover omitted supersession when a last Contract exists. |
| Q82 — traceability error | S16/AC13 now maps each case name to its CP01-S04 scenario: AC01 done, the AC06 standalone control, AC06 two-current-briefs, and AC07 proceed-to-reject. |

Rejected alternatives:
- Q79: failing the whole graph for one unreachable record. This contradicts Core §44's per-Intent derivation.
- Q79: silently ignoring the record. This contradicts Core §57.
- Q81: requiring a supersession edge on every re-authorisation. This contradicts "when one exists".

## Challenge plan and why

The risks are an implementation that rejects the valid first authorisation, one that hides unreachable records, and a later consumer (S16) that cannot find its referenced scenarios.
