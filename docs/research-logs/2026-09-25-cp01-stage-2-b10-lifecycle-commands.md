# CP01 Stage 2 B10 — Lifecycle command surface and dispatch

**Scope:** batch B10 of the Checkpoint 1 Stage 2 resolution pass: Q26, Q27 and Q33. Revisions, authorisation and method are as in [B7](./2026-09-25-cp01-stage-2-b7-shapes-and-identity.md). **Dependencies:** B8, B9. **Owning clauses:** Core §§27, 44, 46, 49, 54, 58, 60; Distribution §§14, 20; Checkpoint 1 §3, Step 24 prose, exit gate. **Affected IDs:** S08/R01, R02, R03, R05, AC01, AC02, AC09; S10/R05; S12/R07, R08, AC08; Step 24 (version 17 prose).

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q26 — what `run` dispatches at Step 8; whether status/next name Contract-crafting responsibilities: **already specified, made explicit** | Status and next span both lifecycle regions: the Contract-crafting responsibilities derived from broad lineage state and the resolved shape's steps read from execution state; next names a responsibility or shape step with its execution mode and required actor (S08/R01, R02, AC01, as the released runtime did, `207ac08:src/lifecycle/engine.ts`). `run` dispatches each capability-backed automatic responsibility, in either region, through the runtime's single capability-invocation seam, which Step 8 supplies with an instrumented invoker; invoked without an invoker it stops at the first such responsibility with an execution failure naming the missing invoker and simulates nothing (S08/R03, AC02 `no-invoker`; the released `noExecutor` behaved this way). Rejected: status/next limited to shape steps (Core §46 reports "current stage, completed stages" of the whole lifecycle and §27 keeps the seven entries as policy). |
| Q27 — one Intent or every direction: **already specified, made explicit** | Status and next cover every Intent direction in Intent-ID order by default, or one selected Intent, and report an unknown selection as a problem; `run` runs the selected direction or every active direction in Intent-ID order with one result each, and a validation failure stops the whole run (S08/R01–R03, AC09). This preserves the released `--intent` interface (Core §46 "preserves the runtime lifecycle interface already present"; `selectLineages`) and Core §44's concurrent independent directions. Rejected: requiring a selection (breaks the Step 23/25 `lifecycle status` commands); continuing other directions after a validation failure (S08/R07 forbids running on a graph that fails complete-state validation). |
| Q33 — later contracts carrying real-capability dispatch and context consumption: **later-stage concern with an owner decision pending** | Context consumption is already carried: S10/R05 (pack prompts rely on runtime-supplied context) and S12/R07, R08, AC08 (adapter passes Step 9 context) need no change. Whether Checkpoint 1 requires `lifecycle run` to invoke real Agent Pack capabilities is a scope decision recorded as proposal P-CP-24 below; the contracts pin only what both options share: one seam, honest stop without an invoker, no simulation. |

**Challenge plan and why:** the wrong implementations are a `run` that pretends automatic work happened, a status that hides a direction, and a Step 24 that never exercises the lifecycle commands on the packed runtime. Checks: (1) read `207ac08:src/lifecycle/run.ts` and `engine.ts` for the released dispatch seam, direction selection and stop conditions and confirm every pinned behaviour is either the released behaviour or a Core-required tightening; (2) confirm the Claude Code adapter model in `207ac08:src/adapter/commands.ts` (Claude Code performs the responsibility and hands results to the runtime) is the only AI execution surface Core and Distribution define for Checkpoint 1, and that Distribution §20 forbids a provider layer inside Pactwright; (3) confirm Checkpoint 2 continues lifecycle execution "only through `pactwright lifecycle run`" in workflows, so a real invoker has a later owner either way; (4) confirm S08/AC06 already requires next and run for a selected unaffected Intent, so Q27's default-plus-selection answer contradicts no existing case. All hold.

**Applied changes:** S08/R01, R02, R03, R05, AC01, AC02, AC09 and AC10 (with B9). Crosswalk `affects` updated; Q33's `affects` keep S12 and S24.

**Proposals for the owner (not applied):**

- P-CP-24 (Q33), two options, recommendation first:
  - **A (recommended):** amend the Step 24 prose (version 17 form, permitted by Checkpoint 1 §3) to add: "Run `pactwright lifecycle status`, `next` and `run` on the fixture consumer against the real lineage at each position; `run` stops honestly at the configured Gate, at manual entries and, for capability-backed automatic responsibilities, with the missing-invoker execution failure, and simulates nothing." Add to §4 "Explicitly out of scope": "A capability invoker that lets `lifecycle run` call an AI provider itself: Checkpoint 2, where workflows continue lifecycle execution through `lifecycle run`." Consequence: Checkpoint 1's AI execution surface stays the Claude Code adapter (Distribution §§14, 20); the exit-gate line "lifecycle commands … work" is satisfied by the honest-stop behaviour.
  - **B:** require in Step 24 that `lifecycle run` dispatches at least the Delivery and Review responsibilities to the real selected pack through a Claude Code headless invoker rendered by the adapter. Consequence: adds provider invocation, credentials and non-deterministic CI to Checkpoint 1 and a new adapter capability that no Core or Distribution clause currently describes.

**Later owners:** Step 12 (adapter commands invoke capabilities through the same seam, S12/AC02); Step 24 per P-CP-24; Checkpoint 2 for automation-driven `run`.
