| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q21 — where richer shapes come from: **ambiguous requirement, resolved in Checkpoint 1 v27 §4** | Checkpoint 1 declares no persisted lifecycle-shape or extended-policy format. A project's `version: 1` configuration resolves only the built-in `direct` shape, whose Delivery, Review and closure steps take their execution mode from `deliver-brief`, `review` and `prepare-evidence`. Gates, corrective routes and iteration bounds are exercised through the runtime's shape-and-policy definition API with test-only fixture definitions that pass the same resolution rules; an exhausted bound stops progression with the step reported blocking, and configured escalation (Core §34) is a later owner's concern; no fixture definition is loadable from a project's `lifecycle.yml` (a shape key there is an unknown key, S06/AC08 `shape-declaration-in-v1`) and using one writes no configuration (S06/R10). Rejected: a `version: 2` schema (Core §27 requires an explicit versioned schema and migration, and Checkpoint 1 §4 keeps shape persistence unresolved); built-in shapes only (would leave Gate, corrective-route and loop criteria and rules 10–15 without any fixture). |
| Q24 — resolved-shape identity; rules 9 and 10: **later-stage mechanism, interim pin** | Execution state identifies the shape by the name the runtime provides, `direct` for the built-in, as Checkpoint 1's interim identity; no hash, version or lock entry is invented and the final mechanism stays open under Core §23 (S06/R06). Rule 9 fires for a current Brief whose otherwise decodable execution-state document has an absent or empty shape name, and an absent document is not rule 9; rule 10 for a name the runtime does not provide or a recorded step name the resolved shape does not declare (S09/R05). Rejected: a shape hash (Core §§23, 56 forbid inventing one); folding rule 9 into the incomplete-load result (Core §57 lists it separately). |

**Challenge plan and why:** the observable risk is a project reaching a Gate or loop that nothing can configure, or two runtimes disagreeing on what rule 9/10 mean. Checks chosen: (1) confirm no Core, Distribution or Guide clause defines a shape format beyond `version: 1` (`grep -n "version: 2\|shape" docs/specs/*.md docs/checkpoints/00-*.md`: Core §27's draft sentence and §§23/28 "unresolved" text, Distribution §12's matching statement that the `version: 2` / `shape` draft is unreleased, and non-defining mentions in Spec 07, the Guide and Principles); (2) confirm the released decoder rejects unknown stage keys and unknown stages (`207ac08:src/config/lifecycle.ts` `rejectUnknownKeys`, `unknown-stage`), so a shape key in `version: 1` is an incomplete load, not inert data; (3) walk every S06–S09 criterion that needs a Gate, route or loop and confirm each names a fixture definition (S06/AC03–AC07, AC11–AC12; S08/AC03, AC08; S09/AC01); (4) confirm S09/AC01 can produce a rule 9, 10, 11, 14 and 15 fixture under the pin without hand-editing a hash. All four hold on the amended text.
