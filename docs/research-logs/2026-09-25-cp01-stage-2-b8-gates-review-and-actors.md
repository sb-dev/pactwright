# CP01 Stage 2 B8 — Gate authority, Review results and actors

**Scope:** batch B8 of the Checkpoint 1 Stage 2 resolution pass: Q22, Q25 and Q31. Revisions, authorisation and method are as in [B7](./2026-09-25-cp01-stage-2-b7-shapes-and-identity.md). **Dependencies:** B7 (fixture definitions carry the Gates and loops), B9 (Review outcomes and Gate resolutions are execution-state writes). **Owning clauses:** Core §§9, 13, 25, 26, 27, 30, 31, 32, 44, 46, 49, 52, 53, 57. **Affected IDs:** S06/R03, R08, R09, AC02, AC03, AC05, AC08, AC11; S07/R07, R09, R10; S08/R01, R02; S09/R05.

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q22 — Gate authority and resolution recording: **missing requirement, resolved in Core v5 §27** | Policy declares the authority a Gate requires as one or more actor kinds from `human`, `agent`, `automation`, enforced kind-only exactly like `approve-contract.actor` (Core §27). A Gate resolution supplies its actor in the Core §9 `<kind>:<identity>` syntax; execution state records it unchanged as attribution with the Gate and outcome; no Decision is created (S06/R03, AC03 with `second-identity-same-kind` and `invalid-actor-syntax`). Rule 14 reads that record (S09/R05). Rejected: named-identity or role authorisation (Core §§9/27 authorise kinds only; Q16/B4 settled that identity is attribution); recording the resolution in the graph (Core §§28, 31 keep Gate state in execution state). |
| Q25 — latest delivered state, delivery change, closing Review outcome: **missing requirement, resolved in Core v5 §§32, 52, 53** | Execution state records per Brief a delivery sequence that increments when a Delivery step completes, and for each completed Review the sequence it evaluated and its outcome from the runtime's structured result: `may-progress`, `correction-required` naming a declared Delivery step, or `blocked`. The latest delivered state is the current sequence; a delivery change after Review is a later Delivery completion; the closing Review permits closure when the most recent Review completion is at the closing step with `may-progress` for the current sequence (S06/R09, AC11; S07/R09, R10). Capability output that does not map is an execution failure, never a transition. Changes made outside a Delivery step are not delivered state and detecting them is not a Checkpoint 1 closure obligation (recorded limitation, AC11 `out-of-band-change`). Rejected: repository revision per step (needs a commit between every step and Core §56 makes it unavailable on any dirty tree); working-tree content hashing (invents a second repository identity that Core §56 excludes); leaving the vocabulary open (two runtimes would accept different capability outputs and both pass). |
| Q31 — `execution: manual` and reject/defer authority: **already specified, made explicit in Core v5 §27** | A `version: 1` entry with `execution: manual` is never dispatched by `lifecycle run`; status reports it as the blocking step with required actor `human` when the entry declares no `actor` and with its declared kind for `approve-contract`, the released semantics (`207ac08:src/config/lifecycle.ts` `isHumanGate`); the runtime records and checks no actor for responsibilities that leave no Decision, so nothing more can be enforced. `approve-contract.actor` authorises every Decision outcome, proceed, reject and defer, including withdrawal and re-authorisation (Core §9 "the authorised actor … according to repository lifecycle policy"; §27 names one entry) (S06/R08; S07/R07). `automation` is an allowed kind although the released decoder accepted only `human` and `agent` (S06/AC08 `released-v1-automation-actor`), a forward-compatible widening. Rejected: treating manual as "any kind may invoke" with a reported required actor of none (contradicts Core §46's required-actor report and the released behaviour). |

**Challenge plan and why:** the wrong implementations to exclude are a Gate that any well-formed actor can pass, a closure that passes with a stale Review, a Review output that the runtime interprets creatively, and a reject Decision that escapes the actor policy. Checks: (1) trace S07/AC12's five closure defects to an execution-state observation under the new definitions (each maps: superseded-brief → lineage; never-reviewed and unreviewed-delivery-change → no Review completion at the current sequence; blocking-closing-review → outcome not `may-progress`; pending-gate → Gate before closure unresolved); (2) confirm S07/AC04 already exercises `disallowed-kind-reject` and `disallowed-kind-defer`, so Q31's answer adds only the withdrawal case there, the `released-v1-automation-actor` case in S06/AC08 and the manual approve-contract case in S06/AC02; (3) confirm S12/AC03 `review-invents-transition` and `review-requests-evidence` still describe outputs that fail to map or name an undeclared route, so the adapter contract needs no change; (4) confirm the released `ACTORS` set and `isHumanGate` behaviour directly from `207ac08`. All hold.

**Applied changes:** S06/R03, R08, R09, AC02, AC03, AC05, AC08 and new AC11; S07/R07, R09, R10 restated with the execution-state definitions. Crosswalk `affects` updated.

**Proposals for the owner (approved and applied in Core v5 / Checkpoint 1 v27):**

- P-Core-26/27 (Q22): add to Core §27: "A Gate's required authority is declared as actor kinds in the same vocabulary and enforced kind-only; a Gate resolution records its actor as attribution in execution state, never as a graph record." Consequence: places the Gate authority model at its owner instead of by analogy.
- P-Core-32/52 (Q25): add to Core §32: "The runtime's structured Review result states at least whether the reviewed delivered state may progress, requires correction at a named declared Delivery step, or cannot progress, and which delivered state it evaluated; Review may say more, never less." Consequence: §32's "does not define a formal protocol" then reads as "no richer protocol", removing the tension with S06/R09.
- P-Core-53 (Q25): add to Core §53 one sentence stating that "the latest delivered state" is the state the most recent Delivery step produced, and that changes made outside a Delivery step are not delivered state. Consequence: places the recorded Checkpoint 1 limitation (S06/R09, S07/AC13 `post-review-out-of-band-edit`) at its owner, or lets the owner decide that detection is required, which would need a repository-identity rule Core §56 currently excludes.
- P-Core-27 (Q31): add to Core §27: "`approve-contract.actor` authorises the kind of every Decision outcome, including withdrawal and re-authorisation; `execution: manual` means the runtime never dispatches the entry and reports it as blocking with required actor human." The Stage 1 exit record asked Stage 2 to make this explicit in §27 or §49.
