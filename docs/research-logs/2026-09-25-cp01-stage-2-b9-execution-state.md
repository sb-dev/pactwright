# CP01 Stage 2 B9 — Execution-state storage and serialisation

**Scope:** batch B9 of the Checkpoint 1 Stage 2 resolution pass: Q23 and Q32. Revisions, authorisation and method are as in [B7](./2026-09-25-cp01-stage-2-b7-shapes-and-identity.md). **Dependencies:** B8 (what the state records). **Owning clauses:** Core §§13, 28, 54, 55, 56; Guide "Filesystem mutation". **Affected IDs:** S06/R04, R07, R11, AC10, AC12, AC13; S07/R06, AC06; S08/R05, AC05, AC10.

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q23 — ignored, committed or outside the repository: **ambiguous requirement, pinned at contract level** | Execution state is Pactwright-owned ordinary repository content: one document per Brief below a runtime-declared path under `.pactwright/`, read through the Step 1 canonical loader with its own decoder, never a canonical record or a core-store entry, excluded from `project_graph_revision`; an absent document means the Brief has not started its shape (S06/R04, R07, AC13). Ordinary progress therefore dirties the tree exactly as the delivered work it accompanies does, and both are committed together; Core §56's repository-revision rule is unchanged and already treats provenance Pactwright writes the same way ("ordinary repository content … committed before the next pinned execution"). Rejected: an ignored generated file (Core §56 excludes "lifecycle execution state" from the graph revision, which only makes sense for repository content; an ignored file cannot carry a Gate resolution or iteration count across clones or the Checkpoint 2 CI runs that continue work "only through `pactwright lifecycle run`", and §56 forbids reading an ignored input as reconstructed state); storage outside the repository (no owner, no history, no replay). |
| Q32 — serialising execution-state writes: **missing requirement, pinned at contract level** | Every execution-state write, an advance, a Gate resolution or a correction, is atomic and serialised in the Step 7 mutation boundary against other execution-state writes and canonical mutations; a write whose inspected state changed before commit is refused without overwriting the other writer, so no advance is lost and no iteration is counted twice (S06/R11, AC12; S08/AC10). A canonical plan that reads execution state, such as Evidence closure reading the Review outcome, includes that document in its stored base (S07/R06, AC06 `changed-execution-state`). Rejected: a second lock or state database (Core §55: "not a second state database"); last-writer-wins (double-counts iterations and can close on a Review the other writer just invalidated). |

**Challenge plan and why:** the failures to exclude are a Gate resolution silently lost, an Evidence closure committing against a Review outcome that changed after planning, and a state document that the loader inventories as unexpected. Checks: (1) confirm Core §54's unexpected-entry rules apply only to `specs/nodes/`, `specs/graph/` and `specs/extensions/`, and no Stage 1 or Stage 4 contract inventories `.pactwright/` beyond its three named files (`grep -n "\.pactwright/" CP01-S0[1-5].yml CP01-S1[4-9].yml`: only config, lifecycle and lock); (2) confirm S05/AC11's `untracked-file` case already makes an uncommitted state document unavailable for pinned replay, so no Stage 1 change is needed; (3) confirm Core §55's base definition lists inputs "used by the plan", so adding the execution-state document a plan read is a reading of §55, not a widening; (4) confirm Checkpoint 2 (`02-remote-delivery.md`) expects lifecycle continuation through `lifecycle run` across workflow runs, which an ignored file cannot support. All hold.
