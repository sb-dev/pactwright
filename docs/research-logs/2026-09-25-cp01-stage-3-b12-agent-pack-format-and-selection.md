| Q36 — pack content format and compatible-runtime declaration: **missing requirement, resolved in Distribution v4 §5** | The recognised manifest is the released `pack.yml` shape (`207ac08:packages/standard/pack.yml`, decoder `207ac08:src/pack/manifest.ts`): `name` (npm package name, the source identity), `version` (exact), `pactwright` (exact or `^x.y.z` caret range with npm semantics, `207ac08:src/pack/locate.ts` `satisfiesRange`), `capabilities` (capability → declared agent key) and `agents` (`prompt` relative file, optional `skills` resolving to `skills/<name>.md`), every prompt and skill file non-empty, unknown keys rejected with path and cause; a package-distributed pack exposes `pack.yml` and `package.json` through `exports` and its manifest name and version equal the package's (a new tightening: Distribution §12 lock agreement compares the pack version the Pactwright lock records with the package-manager lock, so the two must agree; released `resolvePack` checked only the name); a path-sourced pack has no package to agree with. External Production Skills imports are declared through an optional `production_skills` mapping keyed by family ID with at least `source`, a compatible addition recognised so that a Checkpoint 1 runtime can name each entry as unsupported (S10/R07, AC05) instead of reporting an unknown key; its resolution semantics stay with Distribution §§7–8 and Checkpoint 5. The manifest declares no evaluation cases and no adapter content; a later incompatible change needs an explicit format version and migration. Rejected: adding a format-version key now (the released `@pactwright/standard@0.0.1` must stay readable as the Step 28 baseline, and the recognised key set identifies the shape, as for the released lock in Distribution §12); a project-level import declaration (Distribution §3 and Checkpoint 5 keep Production Skills composed through the pack only). |
| Q35 — source forms; installed or delegated; detection ownership: **ambiguous requirement, resolved in Distribution v4 §§5, 15** | `agent-pack use <source>` accepts a package name, optionally `@<exact-version or ^x.y.z>` recorded as the configured constraint (the caret range of the resolved exact version when none is given, matching the released `init` configuration `^0.0.1` and `pnpm add`), or a `./`, `../` or absolute pack path recorded without a constraint (the released `isPathSource` grammar). A package source resolves from the project's installed packages, then the runtime's own dependencies (released `locatePackage`); when nothing installed satisfies the request, `use` delegates installation as a development dependency to the detected project package manager through the runtime's single package-manager delegation seam, under the Distribution §15 detection rule (`packageManager`, else unambiguous lock state, refuse ambiguity, never switch). `upgrade` requests the configured source at its configured constraint, so the package manager resolves the newest satisfying version and reconciles the package manifest to the constraint, then validates the installed candidate before touching the lock; a failed candidate restores the package manifest and lock or names the previous exact version. Step 11 delivers the seam and proves orchestration through an instrumented seam (S11/AC04, AC05, AC10); Step 19 proves the full detection rule (S19/R02, an input to Q44); Step 23 runs `use` against installed packed artefacts, where no request is needed; real package replacement by `agent-pack upgrade` is proven at Checkpoint 2's component-upgrade step (`02-remote-delivery.md`, "The owning upgrade command performs package replacement … do not preinstall the package"). Rejected: requiring the package to be installed beforehand for every path (contradicts Distribution §15 "Pactwright owns upgrade orchestration", invariant 22 and Checkpoint 2's upgrade step); Pactwright fetching or unpacking packages itself (Distribution §15 forbids a parallel installer). |
| Q34 — what Step 11 locks and runs as sync before Steps 12, 15 and 17: **ordering ambiguity, resolved at contract level (S11/R09)** | Step 11 writes the Distribution §12 version 1 lock's runtime and pack portion, `version: 1`, `runtime.version`, `agent_pack` source/exact version/content hash, `agents` and `skills` hash maps and existing `extensions` entries preserved, through the one resolution path that Step 15 completes with lock agreement and `environment_lock_hash`; Step 11 derives no hash. Sync is the runtime's single sync entry point, whose Distribution §14 steps 1–7 (load, validate composition, assemble agents and skills) run at Step 11 and whose rendering is a seam writing no file until Step 12 supplies the adapter; S11's byte-identity checks on the generated environment therefore hold trivially at Step 11 and are repeated with real rendering by S17/AC06 and with the real lock by S15/AC07, both already present. Rejected: reordering so that Step 11 requires Step 12 or Step 15 (Step 12 renders the selected pack's agents, so it needs selection first; Step 15 needs the selection path to prove `lock.selection-integration`). |

**Challenge plan and why:** the wrong implementations are a runtime that silently installs, fetches or switches packages; a manifest reader that accepts a pack whose package identity disagrees with what the locks record; and a Step 11 that invents a lock shape Step 15 must migrate. Checks: (1) read the released manifest decoder, locator and resolver and confirm every pinned manifest rule is either released behaviour or a Distribution §12 tightening (name/version agreement is the only tightening; it follows from lock agreement); (2) `grep -rn "agent-pack use\|pack\.yml\|production_skills" docs/specs docs/checkpoints/0*.md` and confirm no other document defines a conflicting grammar or a project-level import declaration (Checkpoint 5 line 182 forbids the project-level form; Checkpoint 2 lines 106 and 449 expect the upgrade command to replace packages and `use` to be the explicit selection); (3) confirm the released lock (`207ac08:.pactwright/lock.yml`) has no `version` key and `agent_pack.name`, so the version 1 document Step 11 writes is the Distribution §12 current format, not the released one, and S15/R01 describes the same fields; (4) walk S15/AC07 and S17/AC06 to confirm the later repeats exist and name `agent-pack-use` and `agent-pack-upgrade` cases; (5) confirm Step 23 and Step 25 prose remain valid under the source grammar (`agent-pack use @pactwright/standard` with the pack installed resolves without a request).
