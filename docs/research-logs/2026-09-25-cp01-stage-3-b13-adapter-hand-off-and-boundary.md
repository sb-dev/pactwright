# CP01 Stage 3 B13 — Adapter capabilities, runtime hand-off and the mutation boundary during a step

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q38 — capability per command; how a command reaches the mutation API: **missing requirement, resolved in Core v6 §§35, 46** | Each command invokes one core capability: `/capture-intent`, `/propose-contracts`, `/approve-contract` and `/write-brief` invoke `delivery-specification` (Core §35: understanding Intent, alternatives, selection support, Contract, Brief); `/deliver-brief` and `/prepare-evidence` invoke `delivery-execution`, the latter to state the delivered work and verification facts (a new §35 bullet, matching the released template `207ac08:src/adapter/commands.ts`, which delegated prepare-evidence to `delivery-execution`); `/review` invokes `delivery-review`. The one departure from the released templates is `/capture-intent`, which delegated to no agent: S08/R03 requires every automatic responsibility to be capability-backed, so the mapping is fixed for both paths. A Claude Code command can only run shell commands, so the adapter reaches the runtime through Pactwright-owned hand-off commands under `pactwright lifecycle`, rendered by the adapter and versioned with the runtime: a dispatch command (permitted-next-action check, dispatch record for Delivery/Review steps, Step 9 context) and a result command (structured result → mutation API or execution-state write under Core §55). Their exact spelling is an implementation choice because only the runtime-rendered adapter invokes them; they are adapter protocol, not a public contract (S09/R10 keeps `pactwright context` out of the public contract for the same reason; the released `lifecycle record <stage> --file` was this hand-off for the four graph-marking responsibilities). Core §55 already names CLI and adapter-driven calls as mutation entry points, and S08's "no separate CLI mutation command" concerns `lifecycle run`'s in-process mutations, not the adapter. Rejected: a Node-API-only surface (unreachable from a rendered command); mapping `/prepare-evidence` to `delivery-review` (Evidence states what was delivered and verified; Review's outcome is already recorded in execution state under S06/R09, and S13/R03 compares the executor's claims with the record). |
| Q37 — keeping the executing agent from mutating the Delivery Graph: **ambiguous requirement, resolved in Core v6 §55 (detect and refuse progression)** | Prevention is impossible for an agent with repository write access, and leaving it to `validate` cannot tell a valid hand-written record from a runtime write. The runtime records, at dispatch of a Delivery or Review step, the `project_graph_revision` in the Brief's execution state through the Step 6 boundary; the result command accepts the result only against that revision. Any canonical change since dispatch, by the agent or anyone else, refuses the result as an execution failure reporting the change; execution state does not advance, the step stays current for a fresh dispatch, and the change is reported, never reverted (Core §56 forbids automatic resets). This is the S12/AC03 `deliver-writes-graph` assumption made explicit, plus `canonical-change-by-other`, `result-without-dispatch` and `redispatch-after-abandoned-dispatch` (S12/AC11). It does not contradict S06/R09's "changes made outside a Delivery step are not delivered state; detecting them is not a Checkpoint 1 closure obligation": that sentence concerns closure, while this rule concerns accepting a step's result. Hand-edited execution-state documents (raised by the Stage 2 exit review) are given the standing of hand-edited canonical records: written only through the boundary, visible in repository history, checked by validation, not prevented. Rejected: comparing only the direction's lineage records (adds a second revision protocol for one check; the whole-graph revision is already available and a concurrent other-direction change simply requires a fresh dispatch); asking the command to pass the dispatch revision back (trusts the agent). |

**Challenge plan and why:** the wrong implementations are a prompt that performs runtime work or writes execution state itself, a `/review` whose free text becomes a transition, a Delivery result accepted after the agent wrote a record, and a hand-off surface that becomes a public CLI contract. Checks: (1) read the released templates and rendered commands (`207ac08:src/adapter/commands.ts`, `207ac08:.claude/commands/*.md`) and confirm the two-call shape (ask the runtime first, hand the result to the runtime) is the released behaviour and that only the capability mapping of `/capture-intent` changes; (2) confirm S06/R09 fixes the structured Review result and S08/R03 the single invocation seam, so S12/R08 and R12 cite rather than redefine them; (3) confirm S09/R10 and Checkpoint 3 line 588 forbid only a *required public* `pactwright context` contract, so an adapter-protocol command is permitted; (4) confirm Core §55's stored-base rule already refuses a concurrent canonical change for in-process plans, so the dispatch rule extends it across the agent's work rather than contradicting it; (5) confirm S12/AC03 already assumed detection and refusal (crosswalk `S12.run.14` note) so no criterion weakens. All hold.
