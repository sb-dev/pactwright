| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q39 — how eval executes capabilities and judgement; judge identity; no model in CI: **ambiguous requirement, resolved in Distribution v4 §21** | Eval invokes each case's capability through the S08/R03 capability-invocation seam with the invoker supplied to the runner and judges semantic dimensions through a judge seam with the judge supplied; neither seam is a provider (Distribution §20). Without an invoker every candidate-dependent result is reported as not evaluated and nothing is replayed as the pack's result, so the released runner's silent replay of each case's scripted `reference` (`207ac08:src/eval/case.ts`, `runner.ts`) is replaced by an honest report, the same posture Checkpoint 1 §4 fixes for `lifecycle run`; without a judge, semantic dimensions are reported unjudged (released behaviour). Deterministic assertions alone decide the exit status, which is failure when any evaluated assertion fails or any case was not evaluated (Spec 00 §4: skipped checks cannot pass); semantic results never affect it. The report names the invoker and judge identities used or their absence; pinning a judge so that two runs are comparable is the owner of the first real invoker's concern (Checkpoint 2), and until then the judge field is absent. Checkpoint 1 supplies no provider invoker, so the command-line `pactwright eval` reports its cases as not evaluated and exits with failure, while the repository tests exercise every case and assertion through scripted invokers and judges (S13/AC01–AC07); Step 24's "complete core evaluation dimensions" are proven by that suite against the built runtime and the fixture consumer's `eval` reports not evaluated (Checkpoint 1 v28 Step 24). Rejected: live model calls through the adapter or a Claude Code headless invoker in Checkpoint 1 (§4 defers the invoker to Checkpoint 2, and B10's reviewer caveat required that decision to land before this pass, which it did); recorded outputs (no recording mechanism exists in Checkpoint 1); replaying the scripted reference as the pack's result (a no-op producer that passes). |
| Q40 — baseline/candidate inputs; regression definition; result location: **ambiguous requirement, resolved in Distribution v4 §24** | Each side accepts a pack as `<package-name>@<exact-version>` or a pack directory path; the candidate also accepts a project root whose resolved lock supplies the environment. Both resolve through the Step 11 resolution path to exact identities (source, version, content hash, agent/prompt/skill hashes); a version not installed is acquired through the Step 11 delegation seam into an isolated location, leaving the project's packages and locks untouched, which is how Step 28 resolves `@pactwright/standard@0.0.1` beside the installed `0.0.2`; unresolvable inputs fail naming the input, with no substitution (Distribution §12). Both sides use this runtime's case set, invoker and judge. A regression is a deterministic assertion that passed on the baseline and fails on the candidate, at capability, agent and case, with the pack, prompt and skill components whose identities changed; not evaluated on either side is not comparable; failed→passed is an improvement; differing semantic verdicts are differences for review, never regressions, because judgement varies between runs. Changed components are reported even when nothing was evaluated, which gives Step 28's comparison real content without an invoker. Reports go to standard output or an explicitly named path, never below `.pactwright/`, a canonical store or generated adapter output; committing one is the project's choice (Distribution §23: generated artefacts, not canonical truth). Rejected: a stored evaluation report as a baseline input (nothing in Checkpoint 1 needs it, and it would make results a second identity source); a threshold or aggregate deciding regressions (Distribution §24, Principles §17). |

**Challenge plan and why:** the wrong implementations are an eval that passes without running the pack, a comparison that silently substitutes the installed version for a requested baseline, a semantic verdict counted as a regression, and reports written into Pactwright-owned inputs. Checks: (1) read the released runner and CLI (`207ac08:src/eval/runner.ts`, `cli.ts` `evalCommand`) and confirm the only released behaviours changed are the reference replay and the absence of `--baseline`/`--candidate`, which 0.0.1 never had; (2) confirm Checkpoint 1 §4 and Step 24 v27 already fix the no-invoker posture for `run`, so eval's posture is the same decision, not a new one; (3) confirm Step 28's expected result ("may correctly report no regressions … prove the real released-baseline path") is satisfiable with changed-component reporting and not-comparable cases; (4) confirm Distribution §12's "reacquisition mechanism remains an implementation detail" permits acquisition through the package-manager seam into an isolated location; (5) confirm the exit-gate lines on core eval and baseline/candidate evaluation are satisfiable: cases exist and are proven by scripted invokers, and the released baseline resolves exactly. All hold.
