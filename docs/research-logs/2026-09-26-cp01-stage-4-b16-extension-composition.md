**Scope:** batch B16 of the Checkpoint 1 Stage 4 resolution pass: Q43, Q44, Q50 and Q51. Revisions, authorisation and method are as in [B15](./2026-09-26-cp01-stage-4-b15-init-and-scaffold.md). **Dependencies:** B15 (one-shot composition); B18 consumes this batch's migration declaration (reverse migration) and seam request (version listing). **Owning clauses:** Distribution §§10, 11, 12, 14, 15, 27; Core §§54, 55; Implementation Guide command ownership. **Affected IDs:** S16 `requires`, `inputs`, outputs, R03, R06, R07, R12, AC06, AC07, AC09, AC10; S17/AC06; S19 `inputs`, R07, R10; S11/R08 (one request added).

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q43 — what Step 16 runs as sync; must Step 17 repeat Extension proofs: **ordering ambiguity, resolved at contract level** | The same answer B12 gave Step 11 (S11/R09): sync is the runtime's single entry point. Step 16 now requires Step 12, so at Step 16 that entry point renders through the real adapter and S16/AC01, AC03 and AC14 compare real generated output; Step 17 makes the entry point deterministic over the complete composition and repeats every command that runs sync, including `extension add`, `upgrade`, `disable`, `remove`, `init --agent-pack` and one-shot init (S17/AC06, nine cases). Rejected: reordering Step 17 before Step 16 (Step 17's composition includes enabled fixture Extensions, which Step 16 delivers). |
| Q44 — who owns package-manager detection; must Step 16 apply Step 19's rule: **already specified (Distribution v4 §15, S11/R08)** | B12 placed the seam and its detection rule in Step 11 (`package-manager-delegation`). Step 16 and Step 19 declare it as an `inputs` entry, S16/R12 names the seam and the refusal of ambiguous or absent state before any change (S16/AC06 `ambiguous-package-manager`), and Step 19 proves the full detection matrix (S19/AC03), which every seam user inherits. `extension remove` requests removal of the Extension's package dependency through the same seam (§15). Rejected: a second detector in Step 16 or Step 19 (Distribution §15 has one rule and §25 forbids a parallel installer). |
| Q50 — which command disables and re-enables; disable versus remove: **missing requirement, resolved in Distribution v5 §§10, 27** | A new command `pactwright extension disable <id>` deactivates: the configuration entry stays with `enabled: false`, the lock entry is removed (only enabled Extensions have one, §12), the package stays installed and the owned root is preserved as inactive. `extension remove <id>` additionally deletes the configuration entry and requests removal of the package dependency through the seam. `extension add <id>` re-enables a disabled configured Extension through the normal installation path, registering and fully validating the preserved state before activation, as the released `addExtension` already did for a configured, disabled dependency (`207ac08:src/extension/manage.ts`). Both run sync. One invocation names every Extension it disables or removes, so a dependency and its dependent go together (S16/R07, AC09 `disable-required-dependency`, `remove-dependency-with-dependent`, `disable-state`, `remove-state`; AC10 re-enables through `add`). The command is added to Distribution §§10, 27 and the Guide's command-ownership list; Principles §11 already reads `pactwright extension ...`. Rejected: hand-editing `enabled: false` as the disable mechanism (nothing would then re-resolve the lock, and S17/R04 forbids sync from changing locks); making `remove` mean disable (the released `remove` deleted the entry, and Checkpoints 4, 6 and 7 and Spec 07 distinguish disable from remove). |
| Q51 — how an Extension declares a migration; how its identity is locked: **missing requirement, resolved in Distribution v5 §11** | The manifest gains `graph.migrations`, a list of `{from, to, migration}` where `from`/`to` are format versions or the literal `released-0.0.1`, and `migration` names an export of the registration module; a migration is a deterministic read-only function over the owner's decoded records and tuples, and the runtime performs every write within the §15 atomic change set. A target `graph.format_version` differing from the locked one requires a declared migration or chain applied in order in one change set, otherwise the upgrade fails before any change (S16/R06, AC07 `migration-chain`, AC08 `format-change-without-migration`). The declaration is part of `graph.declaration_hash` and the code of `graph.implementation_hash`, so no separate identity is locked. A reverse migration (older version as `to`) is optional and is what rollback uses (B18; S19/R10). The released-format migration moves each owner's data through its `from: released-0.0.1` entry (S19/R07). Rejected: a separate migration package or registry (Distribution §25 forbids machinery beyond the registration export); "explicit compatibility" without a migration as an alternative to migrating (two readings of §11's old wording; replaced by one rule). |

**Challenge plan and why:** the wrong implementations are a Step 16 whose `extension add` renders nothing or renders through a second path; an Extension command that shells out to a package manager it detected itself; a `remove` that leaves a stale lock entry or a `disable` that leaves the package-manager lock disagreeing with the Pactwright lock; and an upgrade that reinterprets stored bytes because no migration was declared. Checks: (1) confirm S11/R09's seam wording already makes sync one entry point and S12 precedes S16 in step order, so adding S12 to `requires` costs no reordering (`pnpm contracts:check` requires-order rule); (2) `grep -n "extension remove\|extension disable\|enabled: false\|disable" docs/specs/0[2-8]*.md docs/checkpoints/0[2-9]*.md` confirms later checkpoints expect disable and remove as distinct states and none names a disable command, so a single new command conflicts with nothing; (3) confirm §12's "package-backed component versions they both identify" makes a disabled Extension (no Pactwright lock entry, package still installed) agree by construction; (4) confirm the released `removeExtension` deleted the configuration entry and kept the package, so `remove` keeps its meaning and gains only the seam request; (5) confirm §12's `implementation_hash` closure ("the registration module and every package file it imports") already covers migration code, so no lock field is added. All hold.
