# CP01 Stage 4 B17 — Environment lock identity and unsupported Production Skills imports

**Scope:** batch B17 of the Checkpoint 1 Stage 4 resolution pass: Q45 and Q46. Revisions, authorisation and method are as in [B15](./2026-09-26-cp01-stage-4-b15-init-and-scaffold.md). **Dependencies:** B15 (scaffold lock). **Owning clauses:** Distribution §§5, 12, 13; Core §§6, 56, 57; Checkpoint 5 §4. **Affected IDs:** S15/R05, R07, AC02, AC11; S17/R06, AC04; S18/R03, AC06; S09/R06, AC05; S12/R13 (unchanged, cited).

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q45 — `environment_lock_hash` protocol, stability, bytes or meaning: **missing requirement, resolved in Distribution v5 §12** | The protocol is `env1:sha256:<64 hex>`: SHA-256 over the UTF-8 RFC 8785 JCS serialization, without a trailing newline, of the complete decoded `version: 1` lock mapping, whose values are JSON-compatible under Core §6. It hashes meaning, not bytes: key order, quoting, comments and line endings do not change it (a checkout with CRLF conversion or a serialiser change in a later runtime must not change replay identity), and any recorded identity does. Stability across runtimes and platforms is pinned exactly as Core §56 pins `pg1`: same digest for the same lock, a new protocol identifier for any incompatible change, unknown protocols fail pinned replay. Frozen vectors live in `docs/specs/fixtures/environment-lock-env1.json` (four inputs, three stored-byte forms of one of them, and a changed-identity control) with a definition test beside the pg1 one; they are definition fixtures, not verifier evidence. The hash is derived from any completely decoded version 1 lock, including the scaffold lock (B15). S15/R05, AC02, AC11 (`frozen-vectors`, `key-order`, `quoting`, `comments`, `crlf`, `unactivated-scaffold`). S09/R06 now checks the env1 grammar in rule 17 like the other protocols (S09/AC05 `malformed-lock-hash-protocol`), while still not verifying the value; S12/R13 is unchanged, since Core §55 decided in the Stage 3 pass that lock changes across the dispatch gap are caught by the result command's own base rather than the dispatch record. Rejected: hashing the lock file bytes (simplest, but a formatting-only or line-ending change would alter replay identity, and `sha256:` bytes would be indistinguishable from the released graph protocol); leaving the algorithm to implementation (a persisted provenance identity, so not an internal choice under methodology §3). |
| Q46 — how a pack declares an external import; whole environment or bound capabilities: **already specified (Distribution v4 §5, Stage 3 B12/X11)** | A pack declares imports through the recognised manifest's `production_skills` family-ID mapping, and a pack declaring any entry is not accepted by this release, so the whole environment is blocked at selection, never a subset of capabilities. Stage 4 wording is corrected accordingly: S15/R07 states that resolution can meet such a pack only through an installed manifest changed since selection; S17/R06, AC04 and S18/R03, AC06 say "declared by the selected pack's installed manifest", not "configured", since Checkpoint 5 §4 forbids a project-level declaration; those fixtures change the installed manifest after selection, so the unsupported import is reported whatever else the content change reports. Rejected: blocking only the bound capabilities (Distribution §5 and S10/AC05 already refuse the pack, and a partially executable pack would need capability-level lock state §12 does not define). |

**Challenge plan and why:** the wrong implementations are a hash that changes when git rewrites line endings or js-yaml changes quoting, a hash that fails to change when an agent prompt's content hash changes, and a `validate` that accepts any string as a lock hash while later replay owners refuse it. Checks: (1) compute the vectors independently in Python and in the Node test (`tests/environment-lock-vectors.test.ts`): identical bytes and digests, and all three stored forms of the scaffold lock decode to the same mapping; (2) confirm Core §6's value domain (no non-string keys, finite safe numbers, no dates) makes JCS total over lock documents, so no lock needs a special case; (3) confirm S15/AC02's identity cases (runtime, pack version, pack content, agent content, skill content) and S16/AC05 (implementation hash) each change a recorded value and so the hash; (4) `grep -rn "environment_lock_hash" docs/specs docs/checkpoints` confirms consumers (Spec 04, Spec 07, Checkpoints 2, 4, 5) treat it as an opaque runtime-supplied identity, so the grammar binds no later document differently; (5) confirm the Stage 2 record for Q28 left the value "opaque until Step 15 pins its protocol", so the S09 grammar check is the planned consequence, not a reopening. All hold.

**Applied changes:** Distribution v5 §12 (env1 protocol paragraph, vector reference). New `docs/specs/fixtures/environment-lock-env1.json` and `tests/environment-lock-vectors.test.ts`. S15/R05, R07, AC02, AC11. S17/R06, AC04. S18/R03, AC06. S09/R06, AC05. Crosswalk `affects` for Q45 and Q46.

**Later owners:** Graph Review (Spec 04) and GitHub integration (Spec 07) record and verify the tuple; Checkpoint 2 compares local and Actions-resolved hashes; Checkpoint 5 resolves `production_skills`. Remaining blockers: none for Stage 4.
