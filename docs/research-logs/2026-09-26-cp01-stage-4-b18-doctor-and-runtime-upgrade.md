| Q47 — severity of each finding; exit status; machine-readable output: **missing requirement, resolved in Distribution v5 §16** | One rule rather than a list of exceptions. *Action required*: a finding that stops the environment from being activated or executed as configured, or that target-runtime activation needs resolved (invalid or missing required input, migration-required format, no selected pack, lock drift, hash mismatch, runtime incompatibility of a component, missing capability, an Extension that cannot register, unsupported import, generated drift, an interrupted upgrade, a validation failure of the active graph). *Warning*: executable now but a supported operation unavailable or stale (ambiguous or contradicted package-manager declaration; unavailable repository revision during ordinary diagnosis, including an uncommitted execution-state or provenance document, which answers the Stage 2 exit follow-up). *No severity*: installed versions, the detected package manager, an available runtime upgrade, undeterminable availability, inventoried inactive data. The overall result is the highest severity, healthy when none. Exit zero for healthy or warning and non-zero for action required, so Steps 23 and 25's "no action-required issue" is the exit status; `--json` emits the result and every finding with severity, code, message, path and remediation, as the released CLI's `--json` did for every command. Remediation is deterministic only for generated drift (`sync`), a migration-required source and an interrupted upgrade (`upgrade` / `upgrade --to <previous>`), a graph validation failure (`validate`) and a component incompatible with the runtime or drifted from the package-manager lock (its owning upgrade command). S18/R02, R04, R05, R07, AC02 (`no-pack-selected`, `interrupted-upgrade`, severities and remediations per case), AC05 (`ordinary-uncommitted-state-document`), AC07 (healthy), AC10 (exit status and JSON). Rejected: warning exiting non-zero (Step 23's scripted consumer would fail on an uncommitted scaffold); generated drift as a warning (execution through a stale adapter runs the wrong agents). |
| Q48 — re-entry mechanism; hand-off and recovery state; location and lifetime of preserved state: **missing requirement, resolved in Distribution v5 §15** | *Target resolution*: without `--to`, the newest published `pactwright` release, listed through the seam's new version-listing request, that is newer than the installed runtime and inside the declared `pactwright` range of the selected pack and every enabled Extension; none means no change. *Recovery record*: Pactwright-owned ordinary content at a runtime-declared path below `.pactwright/`, written by the old runtime before replacement, holding the attempt and the exact previous bytes of the package manifest, package-manager lock, configuration, lifecycle and lock; never committed by the runtime; removed on completion or rollback; while it exists the project is an interrupted upgrade, so mutation and execution refuse and `doctor` names `upgrade --to <previous>`. Canonical stores need no copy because migrations write within Core §55's atomic boundary. *Re-entry*: a child process; the old runtime invokes the runtime now installed in the project, resolved from the project's installed package and never its own module, handing it the record; every later step runs there. *Failure*: the new runtime restores the recorded bytes, requests the previous exact runtime through the seam and removes the record; if that restoration fails the record stays and `upgrade --to <previous>` completes the recovery. *Runtime-ahead*: the Stage 3 exit review's open item. `@pactwright/standard@0.0.1` declares `pactwright: 0.0.1` exactly, so under the draft S19/R05 no `0.0.1` project could ever reach `0.0.2` (the runtime upgrade would refuse for the pack, and the pack upgrade would refuse for the runtime). Distribution v5 therefore defines the runtime-ahead state: a component whose declared range excludes the target neither refuses the upgrade nor is changed by it; the runtime is replaced, migrations that do not need that component's registration run, the lock records the new runtime with the component unchanged, sync and validate are not run, and the upgrade exits zero reporting each such component as action required with its owning upgrade command. The component upgrades that follow, Checkpoint 2's sequence, restore an executable environment. `pactwright upgrade` without `--to` never enters it, because its target must be inside every declared range. S19 outputs, R01, R05, R12, AC01 (`compatible-newer`, `no-newer-release`, `newer-only-incompatible`), AC05 (`restoration-failure`, `interrupted-after-replacement`), AC12, AC14 (`pack-pins-source-runtime`, `extension-pins-source-runtime`, `component-upgrade-restores`). Execution state: Checkpoint 1 has one execution-state format, so the upgrade neither migrates nor copies those documents (S06/R04 unchanged), and a dispatch record survives an upgrade unchanged (S12/R13 unchanged; Core §55 checks only canonical change across the gap). Rejected: refusing runtime-ahead (the deadlock above; Checkpoint 2 line 106 upgrades the runtime first); upgrading the pack inside `pactwright upgrade` (invariants 21 and 24); an ignored recovery directory (an interrupted upgrade must make the repository revision unavailable, and the runtime owns no `.gitignore` entry); exiting non-zero from runtime-ahead (Checkpoint 2 §3 treats a non-zero step as "recover and do not proceed", which would re-create the deadlock). |
| Q49 — rollback: restore bytes or reverse-migrate; rollback after new records: **missing requirement, resolved in Distribution v5 §§11, 15** | Rollback to `0.0.1` runs the paired reverse migration `owned-stores-v1-to-released-0.0.1` under the current runtime before package replacement, the one exception to post-install work by the new runtime, because `0.0.1` cannot run migrations. It moves each enabled owner's records and tuples back through the owner's declared reverse migration (`to: released-0.0.1`, B16), writes the released unversioned lock and validates with the released decoders; core records are unchanged, `edges: []` stays, execution-state and legacy-closure documents stay in place and are reported as unread by the target. Rollback after new canonical work is supported when every record can be expressed; a record no reverse migration can express, inactive or ambiguous owner data and an interrupted upgrade block it before any write. Pre-migration copies are never retained or restored. S19/R10, AC10 (`rollback-restores`, `rollback-after-new-records`, `rollback-blocked`, `rollback-fails`). Rejected: restoring preserved bytes (valid only until the first new record, so useless for the "explicit rollback" Distribution §15 promises, and it would need a copy of every canonical store in the recovery record); letting `0.0.1` ignore the owner-separated stores (forbidden by §15). |

**Challenge plan and why:** the wrong implementations are a doctor that calls an unactivated scaffold healthy or a warning; an upgrade whose post-replacement steps run old code, or that refuses the only sequence by which a `0.0.1` project can reach `0.0.2`; a recovery record that survives success or is committed; and a rollback that points `0.0.1` at stores it cannot read. Checks: (1) `git show 207ac08:packages/standard/pack.yml` confirms `pactwright: 0.0.1` exactly, and `satisfiesRange` in `207ac08:src/pack/locate.ts` confirms `^0.0.z` is exact, so the deadlock is real for every `0.0.x` release; (2) read Checkpoint 2 §3 (lines 100–110) and Step 7 (lines 660–680): the sequence is runtime first, then an exact pack constraint and `agent-pack upgrade`, which runtime-ahead makes executable; its sentences "Every completed operation must leave a compatible resolved environment" and "the still-compatible selected pack" are inconsistent with the released manifest and are listed for the owner as a Checkpoint 2 follow-up rather than edited here; (3) confirm Distribution §26 invariants 21–27 hold under runtime-ahead (only the runtime changes; post-install work by the new runtime except the explicit rollback exception; explicit `--to` for rollback; migrations still explicit; no partial migration); (4) confirm Core §55's atomic boundary makes a store copy unnecessary and Core §56 makes an untracked record dirty the input base, so an interrupted upgrade refuses pinned execution by existing rules; (5) confirm Step 23 and Step 25 prose accept doctor output only as "no action-required issue", matching the exit rule. All hold.
