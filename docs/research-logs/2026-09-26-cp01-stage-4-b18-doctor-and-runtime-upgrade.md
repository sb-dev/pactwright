| Q47 — severity of each finding; exit status; machine-readable output: **missing requirement, resolved in Distribution v5 §16** | One rule rather than a list of exceptions. *Action required*: a finding that stops the environment from being activated or executed as configured, or that target-runtime activation needs resolved (invalid or missing required input, migration-required format, no selected pack, lock drift, hash mismatch, runtime incompatibility of a component, missing capability, an Extension that cannot register, unsupported import, generated drift, an interrupted upgrade, a validation failure of the active graph). *Warning*: executable now but a supported operation unavailable or stale (ambiguous or contradicted package-manager declaration; unavailable repository revision during ordinary diagnosis, including an uncommitted execution-state or provenance document, which answers the Stage 2 exit follow-up). *No severity*: installed versions, the detected package manager, an available runtime upgrade, undeterminable availability, inventoried inactive data. The overall result is the highest severity, healthy when none. Exit zero for healthy or warning and non-zero for action required, so Steps 23 and 25's "no action-required issue" is the exit status; `--json` emits the result and every finding with severity, code, message, path and remediation, as the released CLI's `--json` did for every command. Remediation is deterministic only for generated drift (`sync`), a migration-required source and an interrupted upgrade (`upgrade`, or `upgrade --to` naming the record's designated recovery target), a graph validation failure (`validate`) and a component incompatible with the runtime or drifted from the package-manager lock (its owning upgrade command). S18/R02, R04, R05, R07, AC02 (`no-pack-selected`, severities and remediations per case; the interrupted-upgrade remediation is exercised by S19/AC05 and AC07), AC05 (`ordinary-uncommitted-state-document`), AC07 (healthy), AC10 (exit status and JSON). Rejected: warning exiting non-zero (Step 23's scripted consumer would fail on an uncommitted scaffold); generated drift as a warning (execution through a stale adapter runs the wrong agents). |
| Q48 — re-entry mechanism; hand-off and recovery state; location and lifetime of preserved state: **missing requirement, resolved in Distribution v5 §15** | *Target resolution*: without `--to`, the newest published `pactwright` release, listed through the seam's new version-listing request, that is newer than the installed runtime and inside the declared `pactwright` range of the selected pack and every enabled Extension; none means no change. *Recovery record*: Pactwright-owned ordinary content at a runtime-declared path below `.pactwright/`, written by the old runtime before replacement, holding the attempt and the exact previous bytes of the package manifest, package-manager lock, configuration, lifecycle and lock; never committed by the runtime; removed on completion or rollback; while it exists the project is an interrupted upgrade, so mutation and execution refuse and `doctor` names `upgrade --to` with the record's designated recovery target. An atomic migration prevents a partial move but not a completed move followed by a later failure, so before a migration runs the record also holds the previous bytes of every canonical file the plan changes or removes and the exact path inventory, entries, types and root existence, of every store the plan touches or creates; the whole upgrade is then reversible through `sync`, `validate` and interruption (owner review 5326242471, finding 2). *Re-entry*: a child process; the old runtime invokes the runtime now installed in the project, resolved from the project's installed package and never its own module, handing it the record; every later step runs there. *Failure*: for a record written before replacement, the new runtime restores every recorded byte and the recorded inventory, canonical files and created directories included, requests the previous exact runtime through the seam, verifies the restored environment loads under its recorded format and removes the record; if that restoration fails the record stays. Each record designates its recovery target, the previous runtime for such a record and the installed runtime for a completion-path record (next item), and `upgrade --to` naming that target is the only upgrade invocation accepted while a record exists (owner review 5326340880 and the fresh review of X37–X39 found the earlier generic wording ambiguous for the completion path). *Entry from the released runtime*: `0.0.1` has no `upgrade` command (`207ac08:src/cli.ts`), so it cannot write the record or hand off; its supported entry is package replacement through the package manager followed by `pactwright upgrade --to <installed version>`, which, when the installed runtime already is the target and the lock is behind it, performs the post-replacement steps itself with no package request; the record it writes carries the post-replacement package files as its baseline and designates the installed runtime as its recovery target, so an interruption at record creation, after the migration or after the lock write is recovered by the same `upgrade --to <installed version>`, which restores every `.pactwright/` file, core store and owner root to source bytes and inventory without a package change (owner reviews 5326299828 and 5326329519). Acceptance of the released-format migration runs against the unchanged published `0.0.1` artefact acquired through the seam, never a rebuilt fixture (finding 3). *Runtime-ahead*: the Stage 3 exit review's open item. `@pactwright/standard@0.0.1` declares `pactwright: 0.0.1` exactly, so under the draft S19/R05 no `0.0.1` project could ever reach `0.0.2` (the runtime upgrade would refuse for the pack, and the pack upgrade would refuse for the runtime). Distribution v5 therefore defines the runtime-ahead state: a component whose declared range excludes the target neither refuses the upgrade nor is changed by it; the runtime is replaced, migrations that do not need that component's registration run, the lock records the new runtime with the component unchanged, sync and validate are not run, and the upgrade exits zero reporting each such component as action required with its owning upgrade command. The component upgrades that follow, Checkpoint 2's sequence, restore an executable environment. When several components pin the old runtime (finding 1), each of `agent-pack use`, `agent-pack upgrade` and `extension upgrade` validates the candidate's own runtime compatibility, dependencies and the complete capability set against the other components as recorded, locks it, defers `sync` until no component remains runtime-incompatible and reports the pending ones; the command repairing the last one runs `sync`, and ordinary execution stays refused until then (S11/R04, S16/R06, S19/R12, AC14 `pack-then-extension`, `extension-then-pack`, `dependent-extensions-pinned`). An unchanged exact or caret pin resolves the same version and reports nothing changed (AC14 `unchanged-pin-no-op`), so the remediation names the constraint change, the component and its current constraint, before the owning command (§16, S18/R05, AC02). `pactwright upgrade` without `--to` never enters runtime-ahead, because its target must be inside every declared range. S19 outputs, R01, R05, R12, AC01 (`compatible-newer`, `no-newer-release`, `newer-only-incompatible`), AC05 (`restoration-failure`, `interrupted-after-replacement`), AC12, AC14 (`pack-pins-source-runtime`, `extension-pins-source-runtime`, `component-upgrade-restores`). Execution state: Checkpoint 1 has one execution-state format, so the upgrade neither migrates nor copies those documents (S06/R04 unchanged), and a dispatch record survives an upgrade unchanged (S12/R13 unchanged; Core §55 checks only canonical change across the gap). Rejected: refusing runtime-ahead (the deadlock above; Checkpoint 2 line 106 upgrades the runtime first); upgrading the pack inside `pactwright upgrade` (invariants 21 and 24); an ignored recovery directory (an interrupted upgrade must make the repository revision unavailable, and the runtime owns no `.gitignore` entry); exiting non-zero from runtime-ahead (Checkpoint 2 §3 treats a non-zero step as "recover and do not proceed", which would re-create the deadlock). |
| Q49 — rollback: restore bytes or reverse-migrate; rollback after new records: **missing requirement, resolved in Distribution v5 §§11, 15** | Rollback to `0.0.1` is completed entirely by the current runtime, the one exception to post-install work by the new runtime, because `0.0.1` can neither run migrations nor read a recovery record (finding 3): it runs the paired reverse migration `owned-stores-v1-to-released-0.0.1`, writes the released lock, validates with the released decoders, removes the record and requests package replacement last; afterwards the published `0.0.1` runtime's own `validate` and `lifecycle status` pass on the project (AC10). A replacement that fails after that leaves a released-format project with no record, which the still-installed runtime reads as migration required and `upgrade --to <current>` migrates forward again. It moves each enabled owner's records and tuples back through the owner's declared reverse migration (`to: released-0.0.1`, B16), writes the released unversioned lock and validates with the released decoders; core records are unchanged, `edges: []` stays, execution-state and legacy-closure documents stay in place and are reported as unread by the target. Rollback after new canonical work is supported when every record can be expressed; a record no reverse migration can express, inactive or ambiguous owner data and an interrupted upgrade block it before any write. Rollback never restores pre-migration copies; the recovery record retains them only for failure recovery of the upgrade that made them. S19/R10, AC10 (`rollback-restores`, `rollback-after-new-records`, `rollback-blocked`, `rollback-validation-fails`, `rollback-fails`). Rejected: restoring preserved bytes as the rollback mechanism (valid only until the first new record, so useless for the "explicit rollback" Distribution §15 promises; the record's copies serve one upgrade's failure recovery); letting `0.0.1` ignore the owner-separated stores (forbidden by §15). |

**Challenge plan and why:** the wrong implementations are a doctor that calls an unactivated scaffold healthy or a warning; an upgrade whose post-replacement steps run old code, or that refuses the only sequence by which a `0.0.1` project can reach `0.0.2`; a recovery record that survives success or is committed; and a rollback that points `0.0.1` at stores it cannot read. Checks: (1) `git show 207ac08:packages/standard/pack.yml` confirms `pactwright: 0.0.1` exactly, and `satisfiesRange` in `207ac08:src/pack/locate.ts` confirms `^0.0.z` is exact, so the deadlock is real for every `0.0.x` release; (2) read Checkpoint 2 §3 (lines 100–110) and Step 17 (lines 647–700): the sequence is runtime first, then an exact pack constraint and `agent-pack upgrade`, which runtime-ahead makes executable; its sentences "Every completed operation must leave a compatible resolved environment" and "the still-compatible selected pack" are inconsistent with the released manifest and are listed for the owner as a Checkpoint 2 follow-up rather than edited here; (3) confirm Distribution §26 invariants 21–27 hold under runtime-ahead (only the runtime changes; post-install work by the new runtime except the explicit rollback exception; explicit `--to` for rollback; migrations still explicit; no partial migration); (4) confirm that Core §55's atomic boundary prevents a partial move but not a completed move followed by a later failure, so the record must copy the bytes and path inventory of every store the plan touches (the first version of this check concluded the opposite and was corrected by owner review 5326242471), and that Core §56 makes an untracked record dirty the input base, so an interrupted upgrade refuses pinned execution by existing rules; (6) confirm from `207ac08:src/cli.ts` that the released runtime has no `upgrade` command, so the entry from `0.0.1` cannot capture the source package files before the package manager replaces them, and the completion path's narrower promise (everything but the two package files restored) is stated rather than implied; (7) confirm that a migration creating an owner root and nested entries is reverted by inventory restoration, not by file deletion alone (S19/AC05, AC07, AC08 compare inventories); (8) walk the three completion-path cut points against the generic record rule and confirm that only `--to <installed version>` is accepted, that `--to 0.0.1` is refused, and that the resulting package, store and record state is stated exactly (S19/AC07); (5) confirm Step 23 and Step 25 prose accept doctor output only as "no action-required issue", matching the exit rule.
