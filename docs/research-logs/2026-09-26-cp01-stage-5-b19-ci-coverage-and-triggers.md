| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q52 — must CI run on every claimed Node major, may the packed consumers carry part of the claim, which operating systems: **ambiguous requirement, resolved in Guide v18 §Package metadata** | CI carries the whole Node claim: one job per Node major that the engines range of any publishable package admits, and no other version, on the GitHub-hosted Linux runner (S20/R05; AC03 checks the matrix equals the admitted majors; AC04 `missing-major`, `unclaimed-major`). The Step 22–23 packed consumers prove packaging on the runtime their fixture runs under and carry no part of the range claim, so the crosswalk's S01.references allocation to Step 23 is packaging only. Operating systems: the packages declare no `os` or `cpu` restriction, so Linux is the only exercised platform and the only one that may be claimed; claiming another needs a CI job on it (AC03; AC04 `os-or-cpu-restriction`, added after independent review). The runtime's current range `>=22 <23 \|\| >=24 <25` admits 22 and 24. Rejected: letting the packed consumers cover one major each (the fixtures run on one runtime and are not gated on a matrix, so a claim would rest on whichever version the fixture host had); a macOS or Windows matrix leg now (nothing claims those platforms and the Guide forbids unexercised claims, not unexercised platforms). |
| Q53 — triggers, required status check, who configures branch protection and how it is evidenced: **missing requirement, resolved in Guide v18 §GitHub Actions** | The workflow runs on pull requests and on pushes to the default branch, and on no other event; there is no merge queue in Checkpoint 1 (S20/R07; AC03; AC04 `extra-trigger`, `missing-trigger`). Superseded pull-request runs are cancelled; default-branch runs complete, so every default-branch commit keeps a result that Step 25's "repository CI passes" can cite (S20/R02; AC04 `cancel-default-branch`). It reports one stable check context, `CI / Verify`, an aggregate job that depends on every matrix job, runs whatever their result and succeeds only when all succeeded (S20/R07; AC01, AC02, AC03; AC04 `missing-aggregate-check`, `aggregate-skips-on-failure`). Step 20's own proof runs the pull-request path only: the workflow cannot reach the default branch before the step is accepted, so AC01 runs the candidate as a pull request, the default-branch trigger and the completing concurrency are proven statically (AC03, AC04), and the first real default-branch run is Step 25's self-hosting commit (owner review, exit record X1). Requiring that context before merge is not a Step 20 obligation: the Guide's "required checks must pass before merge" applies after Checkpoint 2 activates GitHub, and it is repository configuration owned by the repository owner, outside the committed files and outside Pactwright ownership (Spec 07 §34 preserves user-owned rulesets; Checkpoint 2's planner never installs a required check whose workflow is absent). It is recorded in the run configuration under Spec 00 §3, and S20/AC06 checks that the required context recorded for the verification workflow, if any, is `CI / Verify` and not a per-Node-major context. Rejected: making the required check a Step 20 acceptance obligation (nothing in the repository can prove or produce it, and a one-maintainer project may land Step 25 without it under the Guide's ceremony rule); a `merge_group` trigger now (no merge queue exists, and an unexercised trigger is a defect under `extra-trigger`); cancelling default-branch runs (a cancelled run leaves a default-branch commit without a result). |

**Challenge plan and why:** the wrong implementations are a matrix that silently drifts from the engines range, a workflow that reports per-leg contexts so a required check names a Node version that later changes, an aggregate that is skipped when a leg fails and so never reports failure, and a required check that an agent tries to satisfy or configure from inside the repository. Checks: (1) `git show c5992d7:.github/workflows/ci.yml` and `tests/ci-workflow.test.ts` confirm the released Stage 5 workflow already used `pull_request` plus `push` to `main`, a `CI / Verify` aggregate with `if: always()` and an engines-derived matrix test, so the adopted answer pins released behaviour rather than inventing it, and its aggregate needed `if: always()` precisely for `aggregate-skips-on-failure`; (2) `grep -n "required check\|merge queue\|ruleset" docs/checkpoints/02-remote-delivery.md docs/specs/07-github-integration.md docs/checkpoints/00-implementation-guide.md` confirms required checks are named only after Checkpoint 2 activation and that Spec 07 §34 lists rulesets among user-owned state, so the owner-configuration disposition contradicts no later owner; (3) the run configuration is the Spec 00 §3 home for "repository, branch, permitted writes", so recording the required-check state there needs no new field in the contract YAML; (4) the current `package.json` engines range expands to majors 22 and 24 under the single-major clause shape the released test recognised, and no `os`/`cpu` field exists in it, so R05's "no restriction declared" holds on the tree; (5) walk S20/AC01–AC04 against a workflow that runs the matrix on `ubuntu-latest` only and one that adds a macOS leg: the first passes, the second fails `unclaimed-major` only if it adds a version, which is the intended distinction (platform legs are not forbidden, unexercised claims are). All hold.
