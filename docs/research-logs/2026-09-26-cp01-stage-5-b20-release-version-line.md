# CP01 Stage 5 B20 — Release version line and dist-tags

**Scope:** batch B20 of the Checkpoint 1 Stage 5 resolution pass: Q54. Revisions, authorisation and method are as in [B19](./2026-09-26-cp01-stage-5-b19-ci-coverage-and-triggers.md). **Dependencies:** none; B21 consumes the dist-tag rule. **Owning clauses:** Guide §npm release model, §First publication of a package, §Preparing the first supported release, §Public-product progression; Checkpoint 1 header and Step 28; Checkpoints 2–9 headers and release steps. **Affected IDs:** S21/R02, AC01, AC02; Step 28 (unconverted).

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q54 — which version Checkpoint 2 publishes; whether the Guide's mapping is amended: **contradictory requirement, resolved in Guide v18 §npm release model and Checkpoints 2–9 after owner authorisation** | The Guide's `Checkpoint N → 0.0.N` table is a plan that the registry has overtaken: `pactwright@0.0.1` and `@pactwright/standard@0.0.1` were published on 2026-09-01 (registry `time` fields, read on 2026-09-26), npm never reuses a version, and Checkpoint 1 v29 publishes the corrective `0.0.2`, which Checkpoint 2 (header and Step 16) also claims. Two checkpoints cannot publish one version, so the version line must shift: the rule is that each checkpoint publishes the next unused `0.0.x`, a corrective release consumes a number, and the checkpoint file's Release line names it. Under that rule Checkpoint 2 publishes `0.0.3`, Checkpoint 9 publishes `0.0.10`, the first-party package introduction points move with their checkpoints (Project Intelligence `0.0.4`, Graph Review `0.0.5`, Assets/Publication `0.0.6`, Operations `0.0.7`) and `0.1.0` remains the first supported release. Applying it rewrites the Guide's three version tables and every version mention in Checkpoints 2–9 (Checkpoint 3 alone names `0.0.3` twenty times), which are specifications unrelated to Stage 5, so this pass first asked the owner; the owner authorised it on the PR and it is applied: every `0.0.N` in Checkpoints 2–9 shifts to `0.0.N+1` (each of those documents is bumped one version), the Guide's public-content, checkpoint-mapping and package-introduction tables and its `0.0.9` sentences move accordingly, and the specifications' mentions of the released `0.0.1` stay, since they name the real artefact. Stage 5 does not depend on the answer: S21/R02 binds the npm tag to the tag's version line (`v0.0.x` → `next`, `v0.1.0`+ → `latest`), not to a checkpoint number, and Step 28's `v0.0.2` is fixed by Checkpoint 1 v29. Rejected: keeping Checkpoint 2 at `0.0.2` (impossible once Checkpoint 1 publishes it); a prerelease identifier for the corrective release (not a normal SemVer development release under `next`, and `0.0.2` is already the owner's decision in v29). |

**`latest` on the development line (consequence, applied in Guide v18 §npm release model):** the registry shows both packages' `latest` and `next` tags at `0.0.1`, and both versions were published by the owner's npm account, not the workflow. npm gives a package's first publication `latest` whatever tag was requested, so `latest` will point at the bootstrapped `0.0.1` until `0.1.0` unless something moves it. The Guide now states that no `0.0.x` release moves `latest`, the release workflow writes only the tag the version line selects, and public `0.0.x` instructions install an exact version (Steps 27 and 29 already do). S21/R02 forbids any other npm-tag write and AC02 `dist-tag-write` rejects a workflow step that writes one. Rejected: advancing `latest` to each `0.0.x` (the Guide reserves `latest` for the supported line and forbids promoting a defective `0.0.x`; trusted publishing grants a publish credential, not a dist-tag one, so the workflow could not do it without a token); moving `latest` back off `0.0.1` (npm requires a `latest` tag, and the Guide treats a dist-tag move as a recorded emergency Decision).

**Challenge plan and why:** the wrong outcomes are a release step whose version is already taken, a workflow whose tag selection depends on the checkpoint number, and a `latest` that silently advances to a corrective development release. Checks: (1) `curl https://registry.npmjs.org/pactwright` and `.../@pactwright%2Fstandard` read on 2026-09-26: versions `['0.0.1']`, dist-tags `{next: 0.0.1, latest: 0.0.1}`, publisher the owner's account, no `dist.attestations`; (2) `grep -n "Release:" docs/checkpoints/0[2-9]*.md` and Checkpoint 2 Step 16 confirm the `0.0.2` collision and that each later checkpoint names its own version, so a shift is a mechanical rewrite with no semantic branch; (3) `grep -n "0\.0\.[0-9]" docs/checkpoints/00-implementation-guide.md` finds the three tables the shift touches (public-product progression, checkpoint mapping, package introduction points) and the `0.0.9` sentence in §Preparing the first supported release; (4) S21/AC03 `development-line` and `supported-line` distinguish tag selection by version line alone, so the workflow is correct under either numbering. All hold.
