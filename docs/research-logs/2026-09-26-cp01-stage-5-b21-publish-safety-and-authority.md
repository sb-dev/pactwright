# CP01 Stage 5 B21 — Publish rerun safety and release authority

**Scope:** batch B21 of the Checkpoint 1 Stage 5 resolution pass: Q55 and Q56. Revisions, authorisation and method are as in [B19](./2026-09-26-cp01-stage-5-b19-ci-coverage-and-triggers.md). **Dependencies:** B19 (admitted Node major for the release job), B20 (dist-tag rule). **Owning clauses:** Guide §Trusted release workflow, §Release failure, §First publication of a package, §GitHub Actions; Spec 00 §§3, 4 (run configuration; external effects need declared authority and receipts, retries must not duplicate them); Checkpoint 1 Step 28. **Affected IDs:** S21/R01, R03, R04, R05, R06, R07, AC01, AC02, AC05, AC06, AC07, AC08 (new); Step 28 (unconverted).

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q55 — does `pnpm publish -r` skip published versions safely under trusted publishing; must Step 21 prove it with a fixture registry, or is review sufficient: **ambiguous requirement, resolved in Guide v18 §Trusted release workflow and §Release failure** | The workflow does not rely on the package manager's implicit skipping. It publishes each package with its own publish command, only after its own registry check finds the tagged version absent, and skips and reports a version already present, such as one the interactive bootstrap published (S21/R06; AC01; AC02 `recursive-publish`, `publish-without-presence-check`). The rerun proof is automated against recorded registry responses (AC08 `none-published`, `one-published`, `all-published`) and traced by review (AC06), so no fixture registry is needed; the behaviour under test is the workflow's own selection, which recorded responses exercise completely. Release runs queue and are never cancelled (R05). Observed evidence: the `v0.0.1` release run (33495980356, 2026-09-01 10:09 UTC) succeeded with its Publish step taking one second, 25 minutes after the owner's interactive publication of both `0.0.1` versions, and the registry holds no version the run added, so pnpm's recursive publish did skip once; but the pnpm publish documentation read on 2026-09-26 states no skipping rule, so that behaviour is unverified as a stable contract and cannot carry the Guide's "verified safe" condition. Rejected: keeping `pnpm publish -r` and proving its skip with a local registry fixture (proves one pnpm version's behaviour, which the lockfile can change; heavier than the explicit check it would justify); review alone until Step 28 (the first real rerun would be the proof, on a live registry). |
| Q56 — must each publish have a human approval through the environment; how are the environment and trusted-publisher configuration evidenced: **missing requirement, resolved in Guide v18 §Trusted release workflow** | The `npm-release` environment admits deployments from version tags only and names no required reviewer; a ruleset restricts creating version tags to the repository owner. The publish authority is the owner's push of a version tag to accepted default-branch source, which the workflow's assertions bind to the checked-out commit; a reviewer gate would be the same person's second click and would block the safe rerun the Guide requires, while the tag-only environment rule and the trusted-publisher binding to this repository, workflow and environment already stop a branch run or another workflow from publishing (S21/R07; AC07 reads the environment and ruleset from the repository configuration at review time). These are repository and registry configuration outside the committed files, resolved and recorded in the run configuration before a release runs (Spec 00 §3). Evidence of a release: the run's `npm-release` deployment record and, for each version the run published, a provenance attestation naming this repository and workflow, which npm generates automatically under trusted publishing (npm documentation, read 2026-09-26: "npm automatically generates and publishes provenance attestations"; trusted publishing needs npm CLI 11.5.1 or later). S21/R03 keeps provenance enabled and an npm CLI that supports trusted publishing (AC02 `provenance-disabled`, `node-outside-engines`); R04 and AC05 verify the attestation for published versions and accept a skipped bootstrap version without one (`missing-provenance`, `bootstrap-version-kept`). The registry shows no attestation on either `0.0.1` and the `v0.0.1` run published nothing, so trusted publishing has never executed: Step 28's `v0.0.2` run is its first exercise, and the checkpoint text now says so. Rejected: a required reviewer on the environment (see above); evidencing the trusted-publisher entry by reading npm settings (no public API exposes it; the attestation is the receipt Spec 00 §4 asks for); an `approval` binding at Step 21 (the step publishes nothing; the authority is exercised at Step 28, whose conversion owns the binding). |

**Challenge plan and why:** the wrong implementations are a rerun that republishes or errors on a package already present, a workflow whose skip depends on a pnpm version, a run that publishes without provenance so the trusted-publisher path is indistinguishable from a token, an environment that any branch run can enter, and a release job on Node 22 whose bundled npm predates trusted publishing. Checks: (1) GitHub Actions API: `release.yml` has exactly one run, on tag `v0.0.1` at `207ac08`, conclusion success, Publish step 10:10:25–10:10:26; registry `time` for both `0.0.1` versions 09:44 UTC the same day, `_npmUser` the owner's account, `dist.attestations` absent, so the OIDC path is unexercised and the skip happened; (2) `git show c5992d7:.github/workflows/release.yml` confirms the released workflow used one `pnpm publish -r` and set `NPM_CONFIG_PROVENANCE`, and its registry step checked the version only, not the tag or attestation, which S21/AC05 `wrong-dist-tag` and `missing-provenance` now distinguish; (3) the npm trusted-publishing page confirms automatic provenance, the 11.5.1 minimum and the `NPM_ID_TOKEN` exchange, so R03's "npm CLI that supports it" is a real constraint (Node 22's bundled npm 10 does not; Node 24's npm 11 does) that the implementation, not the contract, chooses how to meet; (4) walk AC08 against a workflow that publishes both packages in one command: it cannot report `one-published` per package, so the case fails it, which is the intended distinction; (5) `grep -n "trusted" docs/checkpoints/0[3-4]*.md` confirms Checkpoints 3 and 4 bootstrap only a new package interactively and expect "trusted-publisher/provenance expectations" to hold, so the attestation check is what those later owners already assume. All hold.
