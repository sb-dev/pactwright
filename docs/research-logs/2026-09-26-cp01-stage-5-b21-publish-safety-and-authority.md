| Q55 — does `pnpm publish -r` skip published versions safely under trusted publishing; must Step 21 prove it with a fixture registry, or is review sufficient: **ambiguous requirement, resolved in Guide v18 §Trusted release workflow and §Release failure** | The workflow does not rely on the package manager's implicit skipping. It publishes each package with its own publish command, only after its own registry check finds the tagged version absent, and skips and reports a version already present, such as one the interactive bootstrap published (S21/R06; AC01; AC02 `recursive-publish`, `publish-without-presence-check`). The rerun proof is automated against recorded registry responses (AC08 `none-published`, `one-published`, `all-published`) and traced by review (AC06), so no fixture registry is needed; the behaviour under test is the workflow's own selection, which recorded responses exercise completely. Release runs execute one at a time under a concurrency group that retains pending runs (`queue: max`) and cancels none; the platform's default single pending slot cancels an older pending run when a newer arrives, and `queue: max` retains up to 100 pending runs before cancelling further ones (GitHub concurrency documentation, read 2026-09-26), so "never cancelled" holds within that bound and R05 says so (AC01; AC02 `default-queue`; AC06 traces three tags pushed during a run and states the bound; owner review, exit record X3). The same page states that retained runs start in FIFO order by the time each began waiting, not by dispatch, and that ordering is not guaranteed, so the workflow assumes no order (R05; owner review, exit record X21). The outcome of an out-of-order start is decided rather than left to chance: the assertions refuse, before any publish, a release whose expected npm tag already points at a higher version, naming it superseded; a superseded release publishes nothing further, is not rerun, its version number is consumed and its content ships in the next version, which the owner tags (R02, R06; Guide §Release failure; AC04 `dist-tag-ahead` as the out-of-order start, `partial-then-superseded` as the rerun of a half-published release after a higher version; AC06 traces three tags starting in an order that differs from their push order). This keeps R06's no-backwards-move rule true under any order. Rejected: serialising by version intent so that every retained tag publishes (the older version would still have to publish under the dist-tag the higher one holds, which npm cannot do without moving the tag back or inventing a throwaway tag, and a workflow-side reordering would need state the platform does not give it); refusing any release when a higher version tag merely exists in the repository (deterministic, but it discards a valid release that would have published first in the normal order). Observed evidence: the `v0.0.1` release run (33495980356, 2026-09-01 10:09 UTC) succeeded with its Publish step taking one second, 25 minutes after the owner's interactive publication of both `0.0.1` versions, and the registry holds no version the run added, so pnpm's recursive publish did skip once; but the pnpm publish documentation read on 2026-09-26 states no skipping rule, so that behaviour is unverified as a stable contract and cannot carry the Guide's "verified safe" condition. Rejected: keeping `pnpm publish -r` and proving its skip with a local registry fixture (proves one pnpm version's behaviour, which the lockfile can change; heavier than the explicit check it would justify); review alone until Step 28 (the first real rerun would be the proof, on a live registry). |
| Q56 — must each publish have a human approval through the environment; how are the environment and trusted-publisher configuration evidenced: **missing requirement, resolved in Guide v18 §Trusted release workflow** | The `npm-release` environment admits deployments from version tags only and names no required reviewer; a ruleset restricts creating version tags to the repository owner. The publish authority is the owner's push of a version tag to accepted default-branch source, which the workflow's assertions bind to the checked-out commit; a reviewer gate would be the same person's second click and would block the safe rerun the Guide requires, while the tag-only environment rule and the trusted-publisher binding to this repository, workflow and environment already stop a branch run or another workflow from publishing (S21/R07; AC07 reads the environment and ruleset from the repository configuration at review time and compares them with the run configuration's record). These are repository and registry configuration outside the committed files. **They do not exist yet:** the repository rulesets endpoint returned an empty list on 2026-09-26, and the owner's review 5327216977 reports the `npm-release` environment with no protection rules and no deployment branch policy (this session's proxy could not read the environment endpoint). Configuring them is therefore an approved prerequisite of Step 21's review, owned by the repository owner: AC07 carries an `approval` binding, `release.authority-configuration`, whose authority is the owner and whose effect is the configured tag-only environment and version-tag ruleset, read back into the run configuration (Spec 00 §3; owner review, exit record X2). Evidence of a release: the run's `npm-release` deployment record and, for each version the run published, a provenance attestation naming this repository and workflow, which npm generates automatically under trusted publishing (npm documentation, read 2026-09-26: "npm automatically generates and publishes provenance attestations"; trusted publishing needs npm CLI 11.5.1 or later). S21/R03 keeps provenance enabled, and R02 asserts before any publish that the job's npm CLI meets the trusted-publishing minimum, since the admitted Node 22 bundles an npm that predates it (AC02 `provenance-disabled`, `node-outside-engines`; AC04 `npm-too-old`, added after independent review); R04 and AC05 verify the attestation for published versions and accept a skipped bootstrap version without one (`missing-provenance`, `bootstrap-version-kept`). The registry shows no attestation on either `0.0.1` and the `v0.0.1` run published nothing, so trusted publishing has never executed: Step 28's `v0.0.2` run is its first exercise, and the checkpoint text now says so. Rejected: a required reviewer on the environment (see above); evidencing the trusted-publisher entry by reading npm settings (no public API exposes it; the attestation is the receipt Spec 00 §4 asks for); a publish `approval` binding at Step 21 (the step publishes nothing; the publish authority is exercised at Step 28, whose conversion owns that binding; Step 21's approval covers only the configured controls). |

**Challenge plan and why:** the wrong implementations are a rerun that republishes or errors on a package already present, a workflow whose skip depends on a pnpm version, a run that publishes without provenance so the trusted-publisher path is indistinguishable from a token, an environment that any branch run can enter, and a release job on Node 22 whose bundled npm predates trusted publishing. Checks: (1) GitHub Actions API: `release.yml` has exactly one run, on tag `v0.0.1` at `207ac08`, conclusion success, Publish step 10:10:25–10:10:26; registry `time` for both `0.0.1` versions 09:44 UTC the same day, `_npmUser` the owner's account, `dist.attestations` absent, so the OIDC path is unexercised and the skip happened; (2) `git show c5992d7:.github/workflows/release.yml` confirms the released workflow used one `pnpm publish -r` and set `NPM_CONFIG_PROVENANCE`, and its registry step checked the version only, not the tag or attestation, which S21/AC05 `wrong-dist-tag` and `missing-provenance` now distinguish;
