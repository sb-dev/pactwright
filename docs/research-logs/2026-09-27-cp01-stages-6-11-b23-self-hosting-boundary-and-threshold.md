| Q60 — fresh init or migration of the released self-hosted project; lock agreement with a workspace-linked pack; the pre-Checkpoint-2 landing process; the self-hosting threshold: **contradictory inputs, resolved at contract level (S25) with an owner approval binding** | *Start state.* The candidate branch holds no Pactwright project state: `defd052` ("refactor: tabula rasa") removed `.pactwright/`, `specs/`, `docs/getting-started.md` and `packages/standard`, while `origin/main` at `c38fa95` still holds the released `0.0.1` self-hosted graph (four lineages, three done and one open Intent) with the unversioned lock. Two starts were compared. **A, fresh init (adopted):** Step 25 runs `init`, `agent-pack use @pactwright/standard`, `sync`, `doctor`, `validate`, `lifecycle status` and `pnpm verify` on a candidate with no project state; the released records remain Git history on the default branch and are neither migrated nor copied (S25/R02, AC02). **B, migrate the released project:** retain `main`'s `.pactwright/` and `specs/` in the candidate and run `pnpm pactwright upgrade --to 0.0.2` through S19/R01's completion path. B is infeasible under the accepted contracts: the released lock records the `0.0.1` pack content hash, the workspace now links `packages/standard` at `0.0.2` with different content, S19/R07 and Distribution §15 check the source lock against its installed environment before changing it, and S15/R03 rejects content whose hash does not match its recorded identity; `agent-pack use` cannot re-select first because S15/AC06 refuses selection on a migration-required lock. B would need a bespoke self-hosting exception in Distribution §15, which Principles §20 and the Stage 4 records forbid. The Stage 2 exit record (X1) assumed B when it reasoned about "this repository's two 0.0.1 Evidence records (Step 25)"; that rule (legacy-closure documents) stays correct for every migrated `0.0.1` project (S19/AC07, AC13) and loses only this one instance. Consequences of A: the exit-gate line "the `0.0.1` public content set … is delivered through Pactwright and included in the tagged release source" is met by the Step 26 and 27 lineages in the `0.0.2` source; the current `CHANGELOG.md` cites `evidence-…-ee25a0b4`, a `main` record absent from the candidate, so the release preparation must cite only Evidence in the tagged source (B25); the candidate's landing removes the released records from the default branch head, which is the T5 retained-and-replaced boundary for project state and needs the owner's approval, recorded as `self-host.boundary-approval` (S25/AC02) rather than assumed. *Lock agreement.* pnpm records a workspace dependency as `link:packages/standard` with no version, so the two locks identify no pack version in common; agreement rests on the runtime version, which is the root package's own version, and on the pack's content identity against the linked directory (Distribution §12 "versions they both identify"; S25/R03, AC03). A changed `packages/standard` is caught by `doctor` and refused by `sync` until `agent-pack use @pactwright/standard` re-locks it (S15/R03, S17/AC03 `tampered-content`, S14/AC05 `same-selection`), so the self-hosted repository has one supported way to follow pack edits. The runtime is the root package and `pactwright` is not added as a dependency of its own repository (version 14 Stage 7 note; S25/R01). *Landing.* "The repository process available before Checkpoint 2 product GitHub integration exists" is a pull request merged by the repository owner with `CI / Verify` passing on the pull request and on the resulting default-branch commit, the first real default-branch run the Stage 5 pass allocated to this step (S20/AC01; S25/R05, AC05 with `self-host.landing-authority`); GitHub stays disabled in configuration and no Pactwright-generated workflow exists. *Threshold.* Principles §3 and OSS §16 leave the threshold open; Spec 00 T5 and §6 require it declared. It is the acceptance of Step 25: from then, every step whose candidate changes committed files of the Pactwright repository, other than Pactwright-owned generated or execution-state files and the Step 28 release commit, delivers the change through a lineage in the repository's own graph, corrective re-runs included (CP01/R02, AC02; S25/R07; B27). Rejected: importing the released records as new records under the corrected runtime (rewrites history as current truth, Core §45); a direct push to the default branch (S20/AC01 and Q53 already made the pull-request path the proof of CI); deferring the threshold to "when mature enough" (the indefinite excuse Principles §3 forbids). |

**Challenge plan and why:** the wrong implementations are a Step 25 that hand-writes or copies `.pactwright/` files, a migration that silently accepts a pack whose content changed, a self-hosting commit that never runs CI on the default branch, and a threshold nobody can point to. Checks: (1) `git show defd052 --stat` and `git ls-tree -r origin/main` establish the two states above; (2) `git show 207ac08:.pactwright/lock.yml` and `207ac08:packages/standard/pack.yml` confirm the released lock pins pack `0.0.1` content and `pactwright: 0.0.1`, so under `0.0.2` the pack is runtime-ahead *and* content-mismatched, and the mismatch is the fatal one; (3) read S15/R03, S15/AC06, S19/R07 and Distribution §15's released-lock row to confirm no accepted path re-locks a changed pack during migration; (4) walk S14/AC05 and S11/R01 to confirm re-running `agent-pack use` with the configured source re-resolves and re-locks changed content, giving S25/AC03 `pack-content-change` a real mechanism; (5) confirm `pnpm-lock.yaml` records workspace packages as `link:` entries without versions (`version: link:packages/standard` in `pnpm-lock.yaml` at `0f81839`), so S25/R03's agreement rule follows Distribution §12 rather than amending it; (6) confirm Checkpoint 2 v18 Step 17 starts Kakeibo at `0.0.2` and never assumes the Pactwright repository migrated from `0.0.1`, so option A contradicts no later checkpoint; (7) `grep -n "threshold" docs/specs/08-*.md docs/checkpoints/00-implementation-principles.md docs/research-logs/2026-09-26-cp01-task-3-*.md` confirms the threshold is open in OSS §29, Principles §3 and expected as declared by the Task 3 plan (§13), so CP01/R02 supplies what those documents ask for without changing them.
