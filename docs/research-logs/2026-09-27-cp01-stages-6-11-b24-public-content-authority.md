# CP01 Stages 6–11 B24 — Public-content authority, proven behaviour and the learning material

**Scope:** batch B24 of the Checkpoint 1 Stages 6–11 pass: Q61. Revisions, authorisation and method are as in [B22](./2026-09-27-cp01-stages-6-11-b22-packed-consumer-proofs.md). **Dependencies:** B22 (packing procedure and fixture), B23 (landing process, threshold). **Owning clauses:** OSS §§3, 11, 14, 16, 17, 18, 24; Principles §§7, 14, 15; Guide §Public-product progression, §Public-content authority before Project Intelligence, §npm release model, §Test layers; Distribution §§15, 16, 27; Core §§46, 49; Checkpoint 1 §1, Stage 8 and 9 headings. **Affected IDs:** S26 (all), S27 (all); Checkpoint 1 Stage 8 and 9 headings.

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q61 — approving actor; verifiable "proven behaviour"; command coverage; exact version before publication; stale `0.0.1` wording: **ambiguous and stale requirements, resolved at contract level (S26, S27) and in Checkpoint 1 v31 headings** | *Actor.* Public work before Project Intelligence needs an authorised Decision and selected Contract that carry the identity, positioning and product claims (OSS §18, Principles §7, Guide); the repository owner is that authority, so each Step 26 and 27 Contract is an `approval` binding (`content.quick-start-contract-approval`, `content.learning-path-contract-approval`) and a claim the Contract does not authorise, or one the model invents, is a Review failure rather than a style note (S26/R02, AC01, AC04; S27/R03, AC01, AC06). *Proven behaviour.* A verifiable rule: every command and behaviour the material documents is proven by an accepted Checkpoint 1 criterion result or by the Step 23 and 24 packed-consumer evidence of the same candidate revision; the claim check compares each command against that inventory and the shipped CLI, and the material is executed command by command in a clean packed-consumer fixture built from archives of the candidate revision (S26/R03, R04, AC02, AC03; S27/R02, R05, AC02–AC04). Controls inject an unproven command, a floating install line, a cross-document disagreement and a future capability. *Coverage.* "The core distribution commands shipped" are Distribution §27's surface as the release ships it; a new user must understand, install, execute and upgrade, so the material covers installation, both initialisation paths, `doctor`, `validate`, `lifecycle status`, the seven commands with their permitted mutations, `pactwright upgrade`/`--to`, `agent-pack upgrade` and the honest no-invoker posture of `lifecycle run` and `eval`, and documents no Extension, GitHub integration or Project Intelligence as available (S27/R02). The upgrade instructions are exercised in the fixture, where `upgrade` reports no compatible newer release (the registry lists no `0.0.x` above the packed version before publication, and after it `0.0.2` is the newest) and `agent-pack upgrade` reports nothing changed (S27/AC04 `upgrade-instructions`; S19/AC01 `no-newer-release`, S11/AC11). *Exact version.* Guide §npm release model (B20) requires public `0.0.x` instructions to install an exact version because `latest` stays at the bootstrapped `0.0.1`; the current README line `pnpm add -D pactwright` is floating and would resolve `0.0.1` after `0.0.2` publishes under `next`. The instruction therefore names `pactwright@0.0.2` from Step 26 on, before the version exists on the registry; the fixture maps that install to the packed archives until Step 28 (S26/R03, AC03; S27/R04, AC04), and Step 28's registry-installed consumer proves it live (S28/R05). *Stale wording.* The Stage 8 and 9 headings ("Complete the `0.0.1` public learning path", "Publish `0.0.1`") and Step 27's expected result ("install/execute/upgrade `0.0.1`") predate the corrective release; the Guide names the content set by `0.0.1` and its `0.0.2` row as "the corrective release of the same content set", so the release is `0.0.2` and `0.0.1` names the content set. Checkpoint 1 v31 reads "Complete the `0.0.2` public learning path" and "Publish `0.0.2`"; the Step 27 summary says so, and the crosswalk note on S27.expected.1 records the reading. Also found: the README at `0f81839` links `docs/getting-started.md`, which the tabula rasa removed, so Step 27 must recreate the guide (S27/R01). Rejected: letting the model decide positioning within an Intent (OSS §28 invariant 21); documenting the floating install line "until publication" (would ship a line that resolves the wrong version); a review-only proof of the material (OSS §14 makes examples executable validation, and a walkthrough is cheap in the existing fixture). |

**Challenge plan and why:** the wrong implementations are a Quick Start that documents commands the packed consumer never ran, a Contract that authorises nothing and lets the model set positioning, an install line that resolves `0.0.1`, and material that a new user cannot follow without the repository. Checks: (1) `grep -n "pnpm add -D pactwright" README.md examples/core-delivery/README.md` at `0f81839` shows floating lines, confirming the B20 finding and the need for S26/R03 and S27/R04; (2) `ls docs/` at `0f81839` has no `getting-started.md` while the README links it, so the guide is missing today; (3) read OSS §24 Core Delivery and the Guide's `0.0.1`/`0.0.2` rows to confirm the content set and the corrective reading; (4) walk S27/R02's coverage list against Distribution §27's surface and Checkpoint 1 §4's out-of-scope list: every listed command is shipped and nothing listed is out of scope, and the Extension commands, though shipped, are documented only as fixture-proven, not as a first-party capability, which "without future Extensions" asks; (5) confirm S19/AC01 `no-newer-release` and S11/AC11 give the upgrade walkthrough deterministic results in a fixture; (6) confirm the claim check's inventory can be derived from accepted criteria and the Step 23/24 evidence without a hand-maintained list (Spec 00 §2: coverage views are generated). All hold.
