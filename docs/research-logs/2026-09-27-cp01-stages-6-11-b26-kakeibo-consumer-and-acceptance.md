Revisions, authorisation and method are as in [B22](./2026-09-27-cp01-stages-6-11-b22-packed-consumer-proofs.md). **Dependencies:** B25 (published `0.0.2`), B23 (threshold does not apply to Kakeibo, whose own Delivery governs), B22 (adapter session and approval pattern). **Owning clauses:** Kakeibo Acceptance Profile §§1–5, 16, 17; Guide §Kakeibo acceptance model, §Execution location, §Test layers; Distribution §§3, 5, 14, 16; Core §§8, 12, 19, 44, 46, 57; Principles §§3, 8, 9, 10, 12, 16, 17; Checkpoint 1 Stage 10 intro, §4; Spec 00 §§3, 4. **Affected IDs:** S29 (all), S30 (all).

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q63 — which step establishes the public-repository foundation; Kakeibo write authority; spec revisions: **contradictory requirement, resolved at contract level (S29, S30)** | The Stage 10 intro permits only the pnpm package/workspace root as pre-Pactwright bootstrap, while the profile's §5 "Required Kakeibo work" also says to establish or verify the smallest public-repository foundation. Both hold if the foundation is not pre-Pactwright work: Step 29 creates only the two bootstrap files where absent, installs `pactwright@0.0.2` from the registry, selects the pack explicitly and inventories the seven foundation items (README, Apache-2.0 LICENSE, SECURITY.md with a private route, CONTRIBUTING.md, the canonical `docs/specs/` set, working deterministic tests, safe synthetic fixtures) without creating any (S29/R01, R04, AC01, AC04); Step 30 delivers each absent item through a Kakeibo Delivery lineage before its acceptance (S30/R08, AC06), which is Principles §3 applied to Kakeibo once Pactwright is installed there. The profile's §5 acceptance lines (Apache-2.0, private security route, no real personal exports, no hidden engine, no research-derived target) become S30/R05, R08, AC03 and AC06. The Kakeibo repository is an external target: its writes and the commits to its default branch need the Kakeibo owner's authority, recorded as `kakeibo.install-authority` (S29/AC05) and `kakeibo.delivery-landing-authority` (S30/AC07), and the run configuration names the repository and the starting revision (Spec 00 §3). The revisions of `docs/specs/README.md` and the 02, 05 and 06 specifications that govern Stage 10 are recorded at Step 29 and cited by the Step 30 Contract; retained Kakeido snapshots in Pactwright are not read (S29/R05; S30/R02; Guide §Kakeibo acceptance model). Rejected: hand-writing LICENSE and SECURITY.md at Step 29 (contradicts the Stage 10 intro and Principles §3); making the foundation a Checkpoint 2 concern (the profile ties it to Checkpoint 1's Kakeibo acceptance, and a public repository without a licence and disclosure route should not receive Delivery output); a `packageManager` field in the bootstrap (pnpm's lockfile makes detection unambiguous under Distribution §15, and the field is Kakeibo's choice). |
| Q64 — deciding actor; invariant list versus the current Kakeibo specification; verifying numeric assertions, the dependency boundary, determinism and the advice rule; invariant preservation: **ambiguous requirement, resolved at contract level (S30)** | The Kakeibo owner authorises the Contract (`kakeibo.contract-approval`, S30/AC01). The checkpoint's thirteen invariants are the profile's §4 "Financial truth" list plus "preparation state does not create reviewed truth" and are the minimum; the current Kakeibo 02 specification at the recorded revision governs the semantics, a difference between the list and the specification is resolved in the specification's favour and recorded as a Step 31 finding, and the Contract cites the specification sections it implements (S30/R02, R03, AC07). Verification is executable: each invariant is a case of `kakeibo.financial-invariants`, passed by the delivered code with explicit numeric assertions where the invariant is quantitative and failed by a variant that violates only it, run twice for identical results (S30/AC02, R10, Kakeibo's own test command); the dependency boundary is a manifest and import scan for Hono, Neon, Cloudflare, UI, analytics and provider packages and for clock, random, network and filesystem modules in domain logic; the advice boundary is a scan for target, percentage and recommendation constants plus review (S30/R04, R05, AC03, AC07). Preservation through the lineage is the Principles §17 failure "a Contract loses a financial invariant", checked by review tracing every invariant through Contract, Brief, Review result and Evidence (S30/R06, AC04). Rejected: an aggregate test-suite pass as the invariant proof (one green run cannot show which invariant a test guards; the violating variants distinguish them); Pactwright-side evaluation cases for Kakeibo invariants (Principles §17 places domain quality with the project; only a repeatable Pactwright responsibility failure becomes a generic case, via Step 31). |

**Challenge plan and why:** the wrong implementations are a Step 29 that scaffolds application infrastructure or edits Kakeibo specs, a Step 30 whose tests pass while an invariant is silently dropped from the Contract, a domain package that imports a Cloudflare binding or reads the clock, a defaulted savings target, and a Kakeibo write made without the owner's authority. Checks: (1) read the profile §5 "Required Kakeibo work" and the Stage 10 intro side by side to confirm the contradiction is real and that the adopted split satisfies both texts verbatim; (2) `grep -n "0\.0\.2\|pnpm-workspace\|packages/domain" docs/checkpoints/02-remote-delivery.md` confirms Checkpoint 2 Step 17 starts from Kakeibo running exact `0.0.2` with `packages/domain` present, so S29/S30's end state is Checkpoint 2's entry state; (3) compare the thirteen invariants with the profile §4 list: twelve match verbatim in substance and "preparation state does not create reviewed truth" comes from §4 "Review truth", so the list adds nothing the profile does not own; (4) walk S30/AC02's fourteen cases against the Intent text to confirm each named semantic has a case and no case lacks an Intent clause; (5) confirm Distribution §15's detection rule makes a lockfile sufficient, so no `packageManager` field is required; (6) confirm Principles §8's Kakeibo list of failures to catch (installation, repository-layout assumptions, onboarding, generated-file ownership) is what S29/AC02 `kakeibo.boundary` and S30/R09 observe. All hold; no Kakeibo repository was read (its current state is outside this session), which is why S29 inventories rather than assumes the foundation.
