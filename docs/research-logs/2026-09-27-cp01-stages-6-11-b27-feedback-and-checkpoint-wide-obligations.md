Revisions, authorisation and method are as in [B22](./2026-09-27-cp01-stages-6-11-b22-packed-consumer-proofs.md). **Dependencies:** B23 (threshold), B25 (fix-forward rule), B26 (Kakeibo findings). **Owning clauses:** Principles §§3, 6, 9, 12, 14, 16, 20, 23; Guide §Transition rule; Core §§4, 7, 44, 46, 47, 56, 57, 59; Distribution §25; OSS §§16, 29; Kakeibo Acceptance Profile §§16, 17; Spec 00 §§2, 4, 5, 6; Checkpoint 1 §4, exit gate. **Affected:** Step 31; `CP01/R02`–`R05`, `AC02`–`AC05`; Guide v19 §Transition rule; the exit-gate preamble.

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q65 — material and blocking; precedence; inventory location; T5 observations: **missing requirement, resolved in Step 31 prose and one Guide sentence** | *Blocking*: a finding that falsifies an exit-gate line or an accepted criterion's evidence, or a documented command of the published release that fails as documented. *Material*, when not blocking: a Pactwright responsibility failure, a manual intervention the runtime or the material should have made unnecessary, a specification-to-implementation deviation or a content gap. *Excluded*, when neither: a Kakeibo-specific domain or product choice exposing no repeatable Pactwright responsibility failure (Principles §16). The order gives each finding exactly one class, and blocking takes precedence: a finding that also meets the material definition is fixed and re-verified, never deferred as an Intent, which Step 31's verify list checks as a control (owner review 5330105036, finding 4). "Each finding worth acting on" is each material finding; each becomes an open Intent with no Decision and no change made for it (Core §7). A blocking fix re-runs the affected steps with re-verification; after Step 25 it is a self-hosted Delivery under `CP01/R02`, and a defect in the published `0.0.2` follows Step 28's fix-forward rule. The inventory is execution evidence outside the Project Graph (Spec 00 §4) and carries the T5 observations on execution friction, code quality, graph behaviour and model and skill effectiveness, without crediting model choice alone. Guide v19 §Transition rule states that before Project Intelligence exists blocking failures are fixed within the checkpoint and material findings become open Intents, which the version 30 Step 31 prose already said and the transition rule left unstated for Checkpoint 1. Rejected: a Decision on each captured Intent; a canonical record type for findings (Principles §20, Core §59). |
| Q66 — the checkpoint-wide obligations and exit-gate ownership: **T2 obligation, resolved in `checkpoint.yml` and the exit record** | Spec 00 §2 declares shared requirements once in `checkpoint.yml` with the checkpoint prefix, inherited by every step as `CP01/R01` is. `CP01/R02` is self-hosting from Step 25's acceptance (B23), exempting the files the runtime writes through its own commands (canonical records and edges, `.pactwright/`, generated adapter output, execution state) and the Step 28 release commit, since lineage records and captured Intents are themselves runtime-written. `CP01/R03` is the graph boundary: only the five core record types and core relations; fixture registrations of the test suite and fixture Extensions packed from it register only in test and consumer fixtures; no Project Intelligence, Graph Review, Assets, Publication, Operations, Experiment, Kakeibo or harness concept enters canonical state; execution state, reports, transcripts, harness evidence and GitHub state stay outside the graph and its revision (Principles §12, Core §§4, 56, profile §16). `CP01/R04` is simplicity: no command, key, format, dependency, package, abstraction or fallback beyond a requirement's need; reuse of the loader, mutation boundary, validators, delegation seam and sync entry point; none of Core §59, Distribution §25 and OSS §29's exclusions. Each has an automated and a review binding; the workspace-package check belongs to simplicity (`AC04`), not the graph boundary, and `AC04` traces each added dependency to a requirement rather than to an undefined declared set (fresh review). `CP01/R05` binds the exit gate: every line needs current evidence of the criteria or step verifications that prove it, with corrections re-verified and external receipts read back. Evidence is current when produced on the revision it names and unaffected by later changes; the revisions are each step's own (the packed revision for Steps 22–24), the tagged release commit for publication, registry and tagged-source lines, the Kakeibo revision for Kakeibo lines, and the final default-branch revision for the self-hosted graph and feedback lines. The first draft demanded the final revision for everything but publication, which would force re-running the real-model Step 24 Delivery at the end (fresh review). The review binding derives the map at review time; the exit record holds this pass's derivation as T2 evidence, not a maintained registry (Spec 00 §2). The exit-gate preamble in Checkpoint 1 names `CP01/R05`. Rejected: exit-gate lines as `checkpoint.yml` criteria (a hand-maintained duplicate); a numeric simplicity metric (Guide §Test layers forbids arbitrary numbers). |

**Challenge plan and why:** the wrong implementations are a Step 31 that captures nothing because "material" is undefined, two classifications for one finding, an inventory stored as graph records, a self-hosting rule a post-Step-25 fix can bypass or that literal reading makes unsatisfiable, a fixture type that leaks into a shipped registry, and an exit gate declared closed on a producer's summary. Checks: (1) neither term was defined in the Guide or Principles before; (2) Core §7 makes an Intent without a Decision valid, so captured Intents pass `validate` and report open (CP01-S08/AC01 `open`); (3) walk `CP01/R02` against Steps 26–31: every committed change after Step 25 is runtime-written, the release commit, or delivered by a lineage (the first draft exempted only generated and execution-state files, which made every lineage's own records and Step 31's Intents fail literally; review found it, corrected); (4) walk `CP01/R03` against Steps 23 and 24: packed fixture Extensions register in consumer fixtures only (the first draft said "confined to the repository test suite", which the consumer fixtures break; corrected); (5) every exit-gate line has at least one proving criterion or step verification (exit record table); (6) `pnpm contracts:check` resolves the `SPEC00` source and its `#2`–`#6` anchors. All hold on the amended text.
