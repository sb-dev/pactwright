# CP01 Stages 6–11 B27 — Findings capture and the checkpoint-wide obligations

**Scope:** batch B27 of the Checkpoint 1 Stages 6–11 pass: Q65 and Q66. Revisions, authorisation and method are as in [B22](./2026-09-27-cp01-stages-6-11-b22-packed-consumer-proofs.md). **Dependencies:** B23 (threshold), B25 (fix-forward rule), B26 (Kakeibo findings); this batch closes the pass. **Owning clauses:** Principles §§3, 6, 9, 12, 14, 16, 20, 22, 23; Guide §Transition rule, §Canonical gap discipline; Core §§4, 7, 44, 46, 47, 56, 57, 59; Distribution §25; OSS §§16, 29; Kakeibo Acceptance Profile §§16, 17; Spec 00 §§4, 5 (T2, T5), 6; Checkpoint 1 §4, exit gate. **Affected IDs:** S31 (all); CP01/R02–R05, AC02–AC05; S25/R07; Guide v19 §Transition rule.

| Question / classification | Adopted answer; alternatives rejected |
|---|---|
| Q65 — definitions of material and blocking; inventory location; T5 observations: **missing requirement, resolved at contract level (S31) with one Guide sentence** | *Material*: a finding that names a Pactwright responsibility failure, a manual intervention the runtime or the material should have made unnecessary, a specification-to-implementation deviation or a content gap. *Blocking*: one that falsifies an exit-gate line or an accepted criterion's evidence, or a documented command of the published release that fails as documented. *Excluded*: a Kakeibo-specific domain or product choice exposing no repeatable Pactwright responsibility failure (Principles §16's question). Every finding gets exactly one classification with its reason (S31/R02, AC01, AC04). Material findings become open Intents through `/capture-intent` in the Pactwright repository, phrased as outcomes and left without a Decision, with no change made for them (S31/R03, AC02; Core §7). Blocking findings are fixed within the checkpoint by correcting the candidate and re-running the affected step contracts with re-verification, a fix after Step 25 being a self-hosted Delivery under CP01/R02 and a defect in the published `0.0.2` following S28/R07 (S31/R04, AC03). The inventory is an execution evidence artefact outside the Project Graph, linking each finding to its Intent ID, fix reference or exclusion reason (S31/R07; Spec 00 §4 keeps run records separate from definitions), and it carries the T5 observations on execution friction, code quality, graph behaviour and model and skill effectiveness without attributing improvements to model choice alone (S31/R01, AC01). Guide v19 §Transition rule gains one sentence stating that before Project Intelligence exists blocking failures are fixed within the checkpoint and material findings are captured as open Intents, which the version 30 Step 31 prose already said and the transition rule's "captured through Project Intelligence" line left unstated for Checkpoint 1. Rejected: a Decision on each captured Intent (they are future work, Core §7 valid incomplete state); a canonical record type for findings (Principles §20 and Core §59; Project Intelligence owns this later). |
| Q66 — checkpoint-wide simplicity, graph-boundary and self-hosting obligations; exit-gate ownership: **T2 obligation, resolved in checkpoint.yml (CP01/R02–R05) and this pass's exit record** | Spec 00 §2 declares shared requirements once in `checkpoint.yml` with the checkpoint prefix, so the three obligations are `CP01/R02` (self-hosting from the Step 25 threshold, B23), `CP01/R03` (graph boundary: only the five core types and core relations are registered, fixture registrations stay in the test suite, no Project Intelligence, Graph Review, Assets, Publication, Operations, Experiment, Kakeibo or harness concept enters canonical state, and execution state, reports, transcripts, harness evidence and GitHub state stay outside the graph and its revision; Principles §12, Core §§4, 56, profile §16) and `CP01/R04` (simplicity: no command, key, format, dependency, package, abstraction or fallback beyond a requirement's need; reuse of the loader, mutation boundary, validators, delegation seam and sync entry point; none of the excluded items of Core §59, Distribution §25 and OSS §29), each with an automated and a review binding (`repo.self-hosted-lineage`/`repo.self-hosting-review`, `repo.graph-boundary`/`repo.graph-boundary-review`, `repo.surface-inventory`/`repo.simplicity-review`), inherited by every step as `CP01/R01` already is. The exit gate keeps its thirty-one lines in the checkpoint file (Spec 00 §2 retains exit obligations) and `CP01/R05`/`AC05` binds it: the checkpoint closes only when every step is accepted, every line has current evidence of the criteria that own it on the final revision, corrections are re-verified and the external receipts are read back, with the review binding `checkpoint.exit-gate` deriving the line-to-criteria map from the contracts at review time rather than from a maintained registry (Spec 00 §2 forbids a second hand-written acceptance registry). The map this pass derived is in the exit record as T2 evidence that later integration proofs are explicitly allocated; it is a record, not a plan. Rejected: putting the exit gate lines into `checkpoint.yml` as criteria (a duplicated, hand-maintained mapping); a simplicity metric such as dependency or line counts (Guide §Test layers forbids arbitrary coverage numbers; a rubric traced to requirement IDs is what review can judge). |

**Challenge plan and why:** the wrong implementations are a Step 31 that captures nothing because "material" was never defined, an inventory written as graph records, a self-hosting rule that a code fix after Step 25 can bypass, a fixture Extension type that leaks into the shipped registry, and an exit gate declared closed by a producer's summary. Checks: (1) `grep -n "material\|blocking" docs/checkpoints/00-implementation-guide.md docs/checkpoints/00-implementation-principles.md` confirms neither term was defined before; (2) confirm Core §7 makes an Intent without a Decision valid, so open captured Intents pass `validate` (S09/AC01 control) and `lifecycle status` reports them open (S08/AC01 `open`); (3) walk CP01/R02's exemptions against Steps 26–31: the release commit (version, lockfile, CHANGELOG) is the only committed change that is not a Delivery, and Pactwright-owned generated and execution-state files are written by the runtime, so every other committed change after Step 25 has a lineage; (4) walk CP01/R03 against S16 and S24: fixture Extensions register through the same declaration path but only in the test suite and the packed test assets, never in the published archives (S24/AC06), so the boundary is checkable on the built registry; (5) confirm every exit-gate line maps to at least one accepted criterion or to a Stages 6–11 criterion (table in the exit record), so `CP01/AC05`'s reviewer has something to derive; (6) confirm `pnpm contracts:check` accepts the new `SPEC00` source key and the `#3`–`#6` anchors, since Spec 00 numbers its sections. All hold.
